# 공유 비동기 연결의 수명주기

## 문제와 변경

SessionService는 Redis client를 재사용하지만 서버 종료에서 닫지 않았다. 실제 로컬 Redis에서 같은 service를 두 이벤트 루프에 사용하면 두 번째 요청이 RuntimeError를 원인으로 SessionStoreUnavailableError가 되는 것을 재현했다. 모델 연결의 순차 종료 또한 앞 연결이 실패하면 뒤 연결 종료를 건너뛰었다.

서버 lifespan은 표준 AsyncExitStack에 종료 작업을 등록한다. 종료 시 활성 분석 작업을 취소·정리한 뒤 모델 연결, Redis 연결 순으로 정리한다. 한 정리 함수가 실패해도 나머지 콜백을 실행한다. 정리 오류는 숨기지 않고 호출자에게 전달한다.

SessionService.close는 기존 Redis 연결 참조를 먼저 초기화한 다음 aclose를 호출한다. 사용하지 않은 연결을 새로 만들지 않으며 반복 호출은 안전하다. 다음 lifespan에서 필요할 때 새 연결을 만든다. Redis TTL 세션·게스트 이력·실행 snapshot을 삭제하지 않는다.

모델 연결은 현재 루프의 캐시를 먼저 비우고 gather(return_exceptions=True)로 모든 종료를 시도한다. 모든 시도가 끝나면 실패/취소를 전달한다. 클라이언트 하나의 종료 실패나 취소 때문에 나머지 연결이 누락되지 않는다. 다른 이벤트 루프의 연결을 강제로 닫지는 않는다.

## 검증

- 모델 연결 하나의 종료 실패/취소에도 다른 연결 종료 및 캐시 제거
- Redis 반복 종료, 실패 시 참조 초기화, 종료 시 설정 조회/연결 생성 없음
- 활성 실행·모델·Redis 순서 및 각 정리 단계 실패 후 나머지 정리
- lifespan task 취소 후 정리 콜백 실행과 취소 전달
- 실제 Redis에서 서로 다른 두 루프의 서버 lifespan을 실행: 다른 pool 생성, 첫 루프에서 발급한 합성 세션을 둘째 루프에서 조회, 기존 TTL 자료 유지

실제 모델 호출 없이 합성 client를 사용하며 Redis 테스트 사용자 ID는 실제 회원이 아닌 음수 값이다. 종료 시간이나 성능 향상 수치는 측정하지 않았다.

## 운영 범위

정리는 정상적인 lifespan 종료 경로에 적용한다. 프로세스 강제 종료·전원 중단을 다루는 영속 작업 큐가 아니다. 종료 중 반복 취소나 클라이언트 종료가 영원히 반환하지 않는 상황에 대해 별도의 강제 종료 기한을 추가하지 않았다. 기존처럼 분석 작업은 프로세스 asyncio task이며 정상 종료 뒤 자동 재개하지 않는다. 실제 회원 데이터나 저장 문맥 구조는 바꾸지 않는다.
