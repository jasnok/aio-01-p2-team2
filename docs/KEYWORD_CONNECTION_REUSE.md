# 하이브리드 검색의 키워드 DB 연결 재사용

## 변경

기존 하이브리드 검색은 추출한 키워드마다 연결을 열고 pgvector 타입을 등록했습니다. `search_documents_by_keywords()`는 한 연결과 커서에서 키워드별 기존 SQL을 실행하고 결과를 입력 순서대로 이어 붙입니다. 단일 키워드 메서드는 같은 배치 경로를 호출합니다. 서비스의 조회 반복문도 배치 호출 하나로 바뀝니다.

SQL 점수, 키워드별 `LIMIT`, 문서 ID 정렬, 가장 적합한 청크와 동점 청크의 순서, 범주·문서 유형 필터, 최종 하이브리드 융합은 그대로입니다. 여러 키워드를 OR로 합쳐 후보 개수나 점수를 바꾸지 않습니다. SQL 파라미터 바인딩도 유지합니다. 빈 목록은 연결을 열지 않으며 오류가 발생하면 커서와 연결의 기존 context manager가 정리합니다.

연결 풀이나 추가 의존성을 도입하지 않았습니다. 벡터 조회는 기존 별도 연결을 사용합니다. 키워드마다 SQL 실행은 여전히 필요하므로 SQL 요청 수 자체를 줄인 변경은 아닙니다. PostgreSQL 기본 READ COMMITTED에서 각 SQL은 개별 문장 시점의 스냅샷을 읽습니다. 실행 중 데이터가 변경되면 고정 스냅샷의 완전한 결과 동일성을 보장하지 않습니다.

## 실제 측정

로컬 PostgreSQL 연결·벡터 등록만 준비 5회 이후 10회 측정한 중앙값은 42.847ms였습니다. 다음 비교는 실제 공개 법률 데이터에서 같은 질문·SQL·점수·제한으로 방식별 2쌍 준비 후 10쌍을 측정하고 실행 순서를 번갈아 배치했습니다. API·임베딩·답변 생성은 호출하지 않았습니다.

| 질문 범주 | 키워드별 연결 중앙값 | 한 연결 중앙값 |
| --- | ---: | ---: |
| 주거 | 325.85ms | 156.35ms |
| 노동 | 263.50ms | 86.46ms |
| 소비자 | 553.32ms | 358.53ms |

각 질문은 5개 검색어를 사용하여 키워드 조회 연결 수가 5개에서 1개로 줄었습니다. 범주별 12쌍의 전체 결과 dict를 비교했으며 모든 쌍이 일치했습니다. 원시 표본과 결과 해시는 [측정 JSON](../output/portfolio/keyword-connections.json)에 저장했습니다. 위 값은 해당 로컬 데이터와 부하에서의 키워드 DB 조회 시간입니다. 전체 상담 응답 개선률이나 검색 관련성 향상을 의미하지 않습니다.

## 재현과 검증

호스트에서 접근 가능한 DB URL을 `DATABASE_URL`로 설정한 뒤 실행합니다. 로컬 Compose의 PostgreSQL 호스트 포트는 5434이며 Docker 내부에서는 postgres:5432를 사용합니다. 연결 정보는 결과 파일에 기록하지 않습니다.

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_keyword_connections.py --output output/portfolio/keyword-connections.json
.\.venv\Scripts\python.exe -m pytest legal_mcp/tests/test_keyword_batch.py -q
```

DB 테스트는 `RUN_POSTGRES_INTEGRATION`이 설정된 경우 실행합니다. 연결별 임시 테이블에서 정확 점수, 본문 점수, 키워드별 제한, 동점 문서/청크, 청크 없는 문서, 범주·유형 제외, 공백과 작은따옴표 검색을 검증하며 기존 데이터에 쓰지 않습니다. 단위 테스트는 빈 목록의 연결 생략, 연결 재사용, 중간 SQL 실패 시 정리, 서비스의 추출 키워드 전달을 확인합니다.

로컬 전체 테스트는 실제 Redis·PostgreSQL 통합 검증을 포함하여 402개 통과·4개 외부 검증 건너뜀을 확인했습니다. Docker MCP 이미지 빌드, `pip check`, HTTP MCP 도구 6개 조회도 성공했습니다.
