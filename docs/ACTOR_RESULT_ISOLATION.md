# AI 결과의 회원·게스트 소유자 분리

## 재현과 변경

분석 조회는 owner_id와 요청 actor.id만 비교했다. 합성 USER 실행에 같은 ID의 GUEST를 넣으면 회원 실행이 반환되는 것을 재현했다. 용어 결과도 owner_role을 저장했지만 조회에서 사용하지 않았다. 동기 질문 캐시는 같은 ID와 멱등 키면 다른 분야·질문에도 이전 답변을 반환했다.

소유자는 `(guest 또는 member, 문자열 ID)`로 식별한다. USER와 ADMIN은 같은 회원 계정 영역이다. 회원 역할 변경 뒤 자신의 결과를 잃지 않으며, 게스트와 회원은 ID가 같아도 서로 다른 소유자다.

- 분석 상태 조회와 SSE 최초 조회는 저장된 actor와 owner_id를 함께 검사한다. 타 소유자는 404다.
- 완료 후 저장 조회는 동일한 검사에서 타 소유자에게 403을 반환한다.
- 분석의 메모리 멱등 키와 Redis v2 예약 키에 소유자 영역을 포함한다.
- Redis 예약 재사용은 저장된 실행의 소유자를 다시 검사한다.
- 용어 결과는 owner_role과 owner_id를 함께 검사한다.
- 동기 질문 캐시는 소유자 영역과 category/question/save_selected/conversation_id/mock scenario를 묶는다. 같은 키의 다른 입력은 409 IDEMPOTENCY_CONFLICT다. session_id는 소유자가 아닌 기존 호환 필드여서 fingerprint에서 제외한다.

## 기존 데이터

실행 snapshot의 actor와 owner_id 표현, TTL, 저장 DB 자료는 변경하지 않는다. 기존 Redis 예약 키는 해당 snapshot이 같은 소유자임을 확인한 경우에만 재사용한다. 다른 소유자의 기존 예약은 존재나 입력 충돌을 노출하지 않고 건너뛴다. actor가 없거나 owner_id와 불일치한 실행은 접근을 허용하지 않는다. 데이터 삭제나 강제 마이그레이션은 수행하지 않는다.

기존 프로세스 메모리 캐시는 배포 재시작 때 사라지는 임시 저장소이며 새 키 형식을 사용한다. 동기 질문 캐시는 계속 프로세스 내부 캐시로서 여러 API 프로세스 간 중복 요청 방지나 동시 요청 병합을 보장하지 않는다. 구버전과 신버전 API를 함께 운영하는 rolling 배포에서 구버전 접근 제어를 보호하지 못하므로 이번 변경을 전체 API 프로세스에 적용해야 한다.

## 검증과 범위

합성 동일 ID로 회원·게스트 분석 조회/저장 차단, 각 영역의 동일 요청 재사용, 용어 조회 차단, USER/ADMIN 동일 회원 유지, 동기 캐시의 입력 충돌을 검사한다. 실제 Redis에서 두 영역의 동시 예약과 각 재사용, 기존 예약의 소유자 확인·충돌 처리·TTL 보존, 용어 결과 교차 접근을 검사한다.

이 문서는 분석·용어 결과 및 그 캐시 경계에 한정한다. 게스트 헤더는 기존 브라우저 식별 방식이며 새 자격 증명 발급 체계는 추가하지 않았다. 게스트 간 식별자 도용 방지, 게시판의 별도 소유자 정책, 공개 배포 보안 전체가 완료됐다는 의미는 아니다. 실제 개인정보나 유료 API 호출 없이 검증하며 성능 향상 수치를 주장하지 않는다.
