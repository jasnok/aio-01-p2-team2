분석 SSE 확정 계약과 Backend 요청

## 활성화

Frontend 구현 완료, Backend 실제 구현·배포와 E2E 검증은 대기입니다.
기본값은 기존 동기 분석 유지입니다. Backend 준비 후 frontend/.env에 설정하고 재시작합니다.

```env
FRONTEND_DATA_MODE=api
FRONTEND_SSE_ENABLED=true
FRONTEND_SSE_TOTAL_TIMEOUT_SECONDS=180
```

SSE 장애 시 동기 POST로 자동 재실행하지 않습니다. 같은 질문 재시도는 저장한 run_id를 조회합니다.
진행 정보는 내부 추론 전문이 아니라 실제 실행 작업·Tool·검색 건수만 전달합니다.

## API

기존 /api/agent-runs Mock 계약을 아래 실제 작업 계약으로 교체합니다.
기존 POST /api/legal/questions와 별도 검색 API는 유지합니다.

1. POST /api/agent-runs
   - JSON: category(housing/labor/consumer), question(trim 후 5~2000자).
   - Header: Idempotency-Key, X-Guest-Id, 로그인 시 Authorization: Bearer token.
   - HTTP 202: {"run_id":"r1","status":"queued"}.
   - 분석을 끝까지 기다리지 말고 백그라운드 작업을 생성한 뒤 즉시 반환합니다.
   - 같은 소유자·Idempotency-Key 재요청은 같은 작업 반환. 다른 본문이면 409.
2. GET /api/agent-runs/{run_id}/events
   - Content-Type: text/event-stream; UTF-8; Cache-Control: no-cache.
   - GET에도 동일한 인증 Header. Last-Event-ID 이후 이벤트를 재전송합니다.
   - 10초 간격 ': heartbeat'와 빈 줄 전송. 프록시 버퍼링을 비활성화합니다.
3. GET /api/agent-runs/{run_id}
   - {"run_id":"r1","status":"running","result":null}.
   - status: queued/running/completed/stopped/failed.
   - completed/stopped의 result는 기존 LegalQuestionResponse 전체이며 is_mock=false.
   - 추가정보 필요: status=stopped, result.termination_reason=needs_clarification,
     result.follow_up_questions에 질문을 포함합니다.
   - failed이면 error: {"code":"...","message":"..."}를 추가합니다.
   - result를 저장한 후 terminal 이벤트를 발행합니다.

작업과 이벤트는 소유자만 접근해야 합니다. ID를 안다고 다른 사용자의 질문·결과에 접근할 수 없어야 합니다.
여러 worker/서버 재시작을 지원한다면 작업 상태·이벤트를 공유 저장소에 보관해야 합니다.
연결 종료는 작업 취소가 아닙니다. 이번 Frontend에는 취소 버튼을 추가하지 않습니다.

## 이벤트

```text
id: 1
event: step.started
data: {"run_id":"r1","step_id":"laws-1","stage":"retrieval","status":"started","tool":"search_laws","message":"관련 법령 검색 중","result_count":null}

```

- id: 작업별 단조 증가 양의 정수. 재전송에서도 같은 id 사용.
- 공통 data: run_id, message. step 이벤트는 step_id, stage, status 포함.
- tool: 실행한 Tool 이름 또는 null. result_count: 완료 검색 건수 또는 null.
- run.started / step.started / step.completed / input.required / run.completed / run.failed만 사용.
- step_id는 실행별 고유 ID이며 동일 작업의 시작·완료 이벤트에서는 동일하게 사용합니다.
- run.started는 status=running, run.completed는 completed, input.required는 stopped, run.failed는 failed.
- 단계는 실제 시작·완료 시 발행합니다. 병렬 Tool은 각각 별도 step_id를 사용합니다.
- MCP 응답을 받기 전 '검색 완료'를 전송하지 않습니다. DB 내부 진행 상태를 모르면 표시하지 않습니다.
- terminal 이벤트는 최종 조회 API에 결과가 준비된 이후 전송합니다.

## Frontend 동작과 제한

- Streamlit 서버가 httpx로 SSE를 수신하며 단계별 상태를 갱신합니다.
- 최초 연결과 최대 2회 재연결, Last-Event-ID로 중복 제거.
- 연결 전/종료 후 작업 조회로 누락된 완료 이벤트를 복구합니다.
- 이벤트 대기 예산 기본 180초, 연결 5초·읽기 무응답 30초 상한.
  일반 상태조회 HTTP 제한시간은 기존 FRONTEND_REQUEST_TIMEOUT_SECONDS를 따릅니다.
- 추가정보는 완료 알림 대신 별도 질문 UI로 표시하고 원질문+추가답변으로 새 작업을 생성합니다.
- 진행·완료 이벤트로 알림/이력을 각각 만들지 않고 최종 결과 처리에서만 기록합니다.
- Session을 잃으면 로컬 run_id도 사라지므로 브라우저 재접속까지의 영구 복구는 후속 범위입니다.
