# 2팀 법률 사례 검색 프로젝트 — 데이터 관리 방향 요약

## 1. 문서 목적

이 문서는 법률 사례 검색 AI Agent 프로젝트에서 다음 데이터를 어디에, 어떤 목적으로 관리할지 정리한 기준 문서이다.

- 법령·판례·공식 사례 원문
- 외부 법률 API 수집 데이터
- RAG 검색용 청크와 임베딩
- 개발·시연용 초기 데이터
- 사용자의 최근 질문과 대화 문맥
- 반복 검색 결과 캐시
- 장기 보존이 필요한 질문 이력

핵심 원칙은 **영구 데이터는 PostgreSQL, 의미 검색 데이터는 PostgreSQL + pgvector, 일정 시간이 지나면 없어져도 되는 데이터는 Redis**에 저장하는 것이다.

---

## 2. 저장소별 책임

| 저장 위치 | 저장 대상 | 보존 성격 | 주요 용도 |
|---|---|---|---|
| PostgreSQL `legal_documents` | 법령·판례·공식 사례의 문서 정보와 원문·출처 | 영구 | 법률 문서의 기준 저장소 |
| PostgreSQL `legal_chunks` + pgvector | 검색용 청크와 임베딩 | 영구, 재생성 가능 | RAG Vector/Hybrid Search |
| PostgreSQL 질문 이력 테이블 | 사용자가 다시 조회해야 하는 질문·답변 | 정책에 따른 장기 보존 | 질의 이력 화면과 감사 추적 |
| Redis | 최근 대화 문맥, 검색 캐시, 임시 처리 상태 | 단기, TTL 적용 | 응답 속도와 후속 질문 처리 |
| `database/seeds/` | 검증된 소량의 초기 법률 데이터 | Git으로 버전 관리 | 개발·테스트·시연 DB 재현 |
| `database/raw/` | 외부 API의 원본 응답 | 선택적 보관 | 장애 분석과 재정규화 |

Redis는 기준 데이터 저장소가 아니다. Redis가 비워지거나 장애가 발생해도 PostgreSQL의 법률 문서와 RAG 검색은 정상 동작해야 한다.

## 3. PostgreSQL에 적재할 법률 데이터

### 3.1 `legal_documents`

법령·판례·공식 상담 사례를 문서 단위로 저장한다.

권장 필드:

| 필드 | 역할 |
|---|---|
| `id` | 프로젝트 내부 문서 식별자 |
| `external_id` | 외부 API가 제공한 원천 문서 식별자 |
| `document_type` | `LAW`, `CASE`, `GUIDELINE` 구분 |
| `category` | `housing`, `labor`, `consumer` 구분 |
| `title` | 사용자와 검색 결과에 표시할 제목 |
| `law_name`, `article_number` | 법령·조문 식별 정보 |
| `case_number`, `court`, `decided_at` | 판례 식별 정보 |
| `summary` | 검색 결과 표시용 검증된 요약 |
| `raw_content` | 청크를 다시 생성할 수 있는 공식 원문 또는 본문 |
| `source_name`, `source_url` | 출처 기관과 공식 원문 링크 |
| `effective_date` | 법령 시행일 |
| `content_hash` | 동일 문서의 내용 변경 여부 확인 |
| `source_updated_at` | 원천 시스템의 수정 시각 |
| `collected_at` | 프로젝트에서 데이터를 수집한 시각 |
| `metadata` | API마다 다른 추가 필드를 보존하는 JSONB |
| `created_at`, `updated_at` | 내부 생성·갱신 시각 |

출처가 불분명하거나 공식 원문을 확인할 수 없는 데이터는 양을 늘리기 위해 적재하지 않는다.

### 3.2 `legal_chunks`

하나의 법률 문서를 RAG가 검색할 수 있는 작은 단위로 분리하여 저장한다.

권장 필드:

- `id`
- `document_id`: `legal_documents.id` 외래 키
- `chunk_index`: 문서 내부 청크 순서
- `content`: 실제 검색 근거가 되는 원문 청크
- `token_count`
- `embedding`
- `embedding_model`
- `embedding_version`
- `created_at`, `updated_at`

청킹 원칙:

- 법령은 조문 단위를 우선한다.
- 판례는 사건 개요, 판단 요지, 결론을 구분한다.
- 너무 긴 구간만 약 500~800 token으로 나눈다.
- 초기 overlap은 약 50~100 token을 사용하고 평가 결과에 따라 조정한다.
- 제목, 카테고리, 법령명, 조문 번호는 임베딩 입력에 문맥으로 포함한다.
- 검색 결과의 출처는 항상 상위 `legal_documents`와 연결한다.

## 4. 외부 API 데이터 관리

### 4.1 기본 권장 방식: 사전 수집

사용자 질문이 들어올 때마다 외부 API를 호출하기보다, 검증된 데이터를 미리 자체 DB에 저장하고 RAG가 검색하는 방식을 기본으로 한다.

```text
외부 법률 API
    ↓
원본 응답 수집
    ↓
프로젝트 공통 Schema로 정규화
    ↓
중복·변경·필수 필드 검사
    ↓
PostgreSQL legal_documents 적재
    ↓
문서 유형별 Chunking
    ↓
Embedding 생성
    ↓
PostgreSQL legal_chunks + pgvector 적재
```

이 방식은 외부 API 장애와 지연의 영향을 줄이고, 동일 문서의 임베딩을 반복 생성하지 않으며, 검색 품질을 재현 가능하게 만든다.

### 4.2 자체 DB 근거가 부족한 경우

필요하다면 외부 API를 보완 경로로 사용할 수 있다.

```text
자체 DB 검색
    ├─ 충분한 근거 있음 → DB 검색 결과 반환
    └─ 근거 부족 → 외부 API 조회
                      ↓
                 응답 정규화·출처 검증
                      ↓
                 현재 요청에 보완 사용
                      ↓
                 검증 후 DB 적재 후보 처리
```

외부 API 응답은 바로 영구 적재하지 않고 다음을 확인한다.

- 공식 데이터인지
- `external_id` 또는 안정적인 식별자가 있는지
- 출처 URL과 날짜가 있는지
- 지원 카테고리에 해당하는지
- 필수 필드가 누락되지 않았는지
- 개인정보나 불필요한 민감정보가 포함되지 않았는지
- 기존 문서의 신규 버전인지 또는 완전한 중복인지

### 4.3 중복과 변경 처리

권장 처리 기준:

```text
external_id가 DB에 없음
→ 신규 INSERT

external_id가 있고 content_hash가 동일함
→ 변경 없음, SKIP

external_id가 있고 content_hash가 다름
→ 문서 UPDATE
→ 기존 청크 교체
→ Embedding 재생성
```

가능하면 다음 유일성 제약조건을 둔다.

```sql
UNIQUE (source_name, external_id)
```

### 4.4 수집 작업 이력

외부 API를 반복 수집한다면 `ingestion_runs` 테이블로 작업 결과를 기록하는 것이 좋다.

- provider
- started_at, finished_at
- status
- fetched_count
- inserted_count
- updated_count
- skipped_count
- failed_count
- error_message

## 5. Seed 데이터의 역할

`database/seeds/`는 운영 DB를 대신하는 저장소가 아니라, 빈 DB를 동일한 상태로 만들기 위한 검증된 초기 입력 데이터이다.

```text
database/seeds/*.json 또는 *.sql
    ↓ ingest_documents.py 또는 seed SQL 실행
PostgreSQL legal_documents
    ↓ chunk_and_embed_documents.py
PostgreSQL legal_chunks + pgvector
```

DB에 적재한 후에도 Seed를 유지하는 이유:

- 팀원이 같은 시연 데이터를 재현할 수 있다.
- Docker 볼륨 초기화 후 다시 적재할 수 있다.
- Docker PostgreSQL과 Supabase에 동일한 데이터를 넣을 수 있다.
- 변경 사항을 Git에서 검토할 수 있다.
- 대표 질문과 기대 검색 결과를 고정할 수 있다.

### JSON과 SQL 선택 기준

- JSON: 외부 API와 연계하고 정규화·청킹·임베딩 파이프라인을 보여줄 때 적합하다.
- SQL: 데이터가 적고 고정적이며 가장 빠른 초기 적재가 중요할 때 적합하다.
- 권장 혼합: DB 구조와 고정 코드값은 SQL, 법률 원천 데이터는 JSON, 적재·임베딩은 Python으로 관리한다.

## 6. Redis 데이터 관리

### 6.1 최근 대화 문맥

후속 질문을 이해하기 위해 최근 메시지 5~10개를 일시 저장한다.

```text
Key: legal:session:{session_id}:messages
Type: List
TTL: 마지막 활동 후 30분
```

메시지가 추가될 때 TTL을 다시 30분으로 갱신하는 Sliding Expiration 방식이 자연스럽다.

저장 권장 항목:

- role
- category
- 질문 또는 최소화된 질문 요약
- 답변 요약
- created_at

저장하지 않을 항목:

- API Key와 비밀번호
- 주민등록번호, 계좌번호 등 불필요한 개인정보
- 장기간 보존할 필요가 없는 민감한 원문 전체

### 6.2 RAG 검색 결과 캐시

동일 조건의 반복 검색 결과를 Redis에 저장하여 응답 시간을 줄일 수 있다.

```text
Key: legal:search:v1:{category}:{query_hash}
TTL: 10~30분
```

캐시 Key에는 가능한 한 다음 조건이 반영되어야 한다.

- 정규화된 질문
- 카테고리
- 문서 유형
- `top_k`
- 임베딩 모델 또는 데이터 버전

DB 데이터나 임베딩 모델이 변경되면 `v1`을 `v2`로 바꾸어 이전 캐시를 사용하지 않게 한다.

### 6.3 질문 이력과 Redis의 한계

Redis TTL이 만료되면 데이터가 자동으로 삭제된다. Redis 재시작이나 운영 정책에 따라서도 데이터가 사라질 수 있으므로, 사용자가 나중에 다시 조회할 질문 이력을 Redis에만 저장해서는 안 된다.

- 최근 대화 문맥: Redis
- 일정 시간 후 없어져도 되는 질문: Redis
- 지난 질문 목록과 답변 재조회: PostgreSQL
- 당시 사용한 법률 근거 추적: PostgreSQL

영구 질문 이력이 필요하다면 `conversation_sessions`, `conversation_messages`, `question_retrievals` 테이블을 추가한다.

## 8. MVP 구현 우선순위

1. `legal_documents`, `legal_chunks` Schema 확정
2. 검증된 대표 Seed 10건으로 적재 확인
3. 문서별 Chunking과 Embedding 생성
4. Vector Search 구현
5. Keyword Search와 Vector Search를 결합한 Hybrid Search 구현
6. MCP Tool의 Mock을 실제 RAG Service 호출로 교체
7. 대표 질문에서 기대 문서가 Top 3에 포함되는지 평가
8. Redis 최근 대화 문맥 적용
9. Redis 검색 결과 캐시 적용
10. 시간이 남으면 PostgreSQL 영구 질문 이력 추가

기능 수보다 다음 흐름이 안정적으로 동작하는 것이 우선이다.

```text
질문
→ Agent
→ MCP Tool
→ RAG Service
→ PostgreSQL + pgvector
→ 출처가 있는 Top 3 근거
→ LLM 정리
→ 사용자 응답
```

## 9. 최종 결정 요약

- 검증된 법령·판례 원문은 PostgreSQL에 저장한다.
- 검색용 청크와 임베딩은 PostgreSQL + pgvector에 저장한다.
- 외부 API는 사전 수집을 기본으로 하고, 필요할 때만 검색 보완 경로로 사용한다.
- 외부 데이터의 식별자, 출처, 수집 시각, 내용 hash를 보존한다.
- Seed는 DB에 적재할 재현 가능한 초기 입력 데이터로 관리한다.
- Redis에는 최근 대화 문맥과 검색 결과 캐시만 단기 저장한다.
- Redis Key에는 용도에 맞는 TTL을 설정한다.
- 사용자가 나중에 다시 조회할 질문 이력은 PostgreSQL에 저장한다.
- Redis 장애 또는 캐시 미스가 발생해도 PostgreSQL 기반 검색은 동작해야 한다.
