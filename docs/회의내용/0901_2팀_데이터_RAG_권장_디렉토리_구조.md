# 2팀 법률 사례 검색 프로젝트 — `database/` 권장 디렉터리 구조

## 1. 문서 목적

이 문서는 프로젝트 전체가 아니라 **`database/` 담당 영역만** 정의한다.

`database/`는 PostgreSQL + pgvector의 구조와 변경 이력, 초기 법률 데이터, 외부 API 원본, 데이터 수집·적재·임베딩 작업 및 RAG 검색 평가 자료를 관리한다.

실제 사용자 요청을 받아 SQL을 실행하는 Repository와 검색 Service 코드는 `legal_mcp/`에서 관리한다. `database/`에는 DB를 준비하고 갱신하고 검증하는 파일만 둔다.

## 2. 최종 권장 구조

```text
database/
│  # 법률 데이터를 PostgreSQL + pgvector에 적재하기 위한 DB 자산을 관리한다.
│  # DB Schema, 초기 데이터, 외부 API 원본, 데이터 처리 스크립트,
│  # RAG 검색 평가 데이터를 이 폴더에서 관리한다.
│
├─ migrations/
│  │  # DB Schema의 생성과 변경 이력을 SQL 파일로 관리한다.
│  │  # 파일명 앞 번호 순서대로 적용한다.
│  │  # 이미 적용된 migration은 수정하지 않고 새 파일을 추가하는 것이 원칙이다.
│  │
│  ├─ 001_init.sql
│  │  # pgvector 확장을 활성화한다.
│  │  # legal_documents와 legal_chunks 초기 테이블을 생성한다.
│  │
│  ├─ 002_search_indexes.sql
│  │  # 카테고리·문서 유형 필터용 인덱스를 생성한다.
│  │  # Keyword Search 및 pgvector 유사도 검색용 인덱스를 생성한다.
│  │
│  └─ 003_ingestion_and_versions.sql
│     # 외부 API 문서 ID, 내용 hash, 수집 시각 등 추적 필드를 추가한다.
│     # 임베딩 모델·버전 필드와 필요 시 ingestion_runs 테이블을 생성한다.
│
├─ seeds/
│  │  # 비어 있는 DB에 최초 적재할 검증된 소량의 법률 데이터를 관리한다.
│  │  # 운영 DB를 대신하지 않으며 개발·테스트·시연 환경을 재현하는 입력이다.
│  │
│  ├─ laws.json
│  │  # 법령·조문 Seed 데이터이다.
│  │  # 법령명, 조문 번호, 원문, 시행일, 공식 출처 URL 등을 포함한다.
│  │
│  ├─ court_cases.json
│  │  # 공식 판례 Seed 데이터이다.
│  │  # 사건번호, 법원, 선고일, 판단 요지, 원문 출처 등을 포함한다.
│  │
│  ├─ guidelines.json
│  │  # 정부기관의 공식 안내·분쟁 조정·상담 사례용 선택 파일이다.
│  │  # MVP에서 사용하지 않는다면 생성하지 않아도 된다.
│  │
│  └─ README.md
│     # Seed별 공식 출처, 수집일, 필드 형식, 적재 명령과 이용 조건을 설명한다.
│
├─ raw/
│  │  # 외부 API에서 받은 가공 전 원본 응답을 선택적으로 보관한다.
│  │  # 재정규화나 수집 오류 분석에 사용한다.
│  │  # 대량 또는 민감 데이터 가능성이 있으므로 기본적으로 Git에서 제외한다.
│  │
│  ├─ laws/
│  │  # 법령 API의 원본 JSON 또는 XML 응답을 보관한다.
│  │
│  ├─ cases/
│  │  # 판례 API의 원본 JSON 또는 XML 응답을 보관한다.
│  │
│  └─ .gitkeep
│     # 원본 파일을 Git에서 제외해도 빈 폴더 구조를 유지한다.
│
├─ evaluation/
│  │  # RAG 검색 단계의 품질을 반복 측정할 평가 데이터를 관리한다.
│  │  # LLM 문장 품질보다 기대 법령·판례가 검색되는지를 우선 평가한다.
│  │
│  ├─ questions.json
│  │  # 평가 질문, 카테고리, 기대 document_id를 정의한다.
│  │
│  ├─ results/
│  │  │  # 검색 평가 결과를 날짜 또는 설정 버전별로 저장한다.
│  │  │
│  │  └─ .gitkeep
│  │     # 결과가 없어도 디렉터리 구조를 유지한다.
│  │
│  └─ README.md
│     # 평가 방법, Top-3 포함률, 통과 기준과 실행 명령을 설명한다.
│
├─ scripts/
│  │  # 서버 요청 코드가 아닌 독립 실행형 데이터 작업을 관리한다.
│  │  # 수집 → 정규화 → 적재 → 청킹·임베딩 → 평가 순서로 실행한다.
│  │
│  ├─ collect_legal_data.py
│  │  # 공식 외부 API에서 법령·판례 데이터를 수집한다.
│  │  # external_id, 출처 URL, 원천 수정일 등 추적 정보를 보존한다.
│  │
│  ├─ normalize_documents.py
│  │  # API별 필드와 날짜 형식을 프로젝트 공통 Schema로 변환한다.
│  │  # document_type·category를 통일하고 필수 출처와 식별자를 검증한다.
│  │
│  ├─ ingest_documents.py
│  │  # 정규화 데이터를 PostgreSQL legal_documents에 적재한다.
│  │  # external_id와 content_hash로 INSERT, SKIP, UPDATE를 판단한다.
│  │  # Docker PostgreSQL과 Supabase에서 동일한 DATABASE_URL을 사용한다.
│  │
│  ├─ chunk_and_embed_documents.py
│  │  # legal_documents 원문을 문서 유형에 맞게 Chunking한다.
│  │  # 각 청크의 Embedding을 생성해 legal_chunks에 적재·갱신한다.
│  │
│  └─ evaluate_retrieval.py
│     # evaluation/questions.json으로 Hybrid Search를 실행한다.
│     # 기대 문서의 Top-3 포함률을 측정하고 검색 설정 조정에 활용한다.
│
├─ .env.example
│  # DB 연결과 데이터 처리 스크립트용 환경변수 예시를 제공한다.
│  # 실제 비밀번호와 API Key는 포함하지 않는다.
│
├─ requirements.txt
│  # 수집, 적재, PostgreSQL, pgvector, Embedding용 Python 패키지를 정의한다.
│
└─ README.md
   # DB 시작, migration, Seed 적재, Embedding 생성, 평가 순서를 안내한다.
```

## 3. 데이터 처리 순서

### 외부 API 사용 시

```text
외부 법률 API
    ↓
scripts/collect_legal_data.py
    ↓
raw/laws 또는 raw/cases
    ↓
scripts/normalize_documents.py
    ↓
프로젝트 공통 형식의 정규화 데이터
    ↓
scripts/ingest_documents.py
    ↓
PostgreSQL legal_documents
    ↓
scripts/chunk_and_embed_documents.py
    ↓
PostgreSQL legal_chunks + pgvector
    ↓
scripts/evaluate_retrieval.py
    ↓
evaluation/results
```

### 검증된 Seed 사용 시

```text
seeds/laws.json + seeds/court_cases.json
    ↓
scripts/ingest_documents.py
    ↓
PostgreSQL legal_documents
    ↓
scripts/chunk_and_embed_documents.py
    ↓
PostgreSQL legal_chunks + pgvector
    ↓
scripts/evaluate_retrieval.py
```

## 4. 폴더별 책임 요약

| 경로 | 책임 |
|---|---|
| `database/migrations/` | PostgreSQL + pgvector Schema와 변경 이력 관리 |
| `database/seeds/` | 검증된 초기 법률 데이터와 출처 관리 |
| `database/raw/` | 외부 API의 가공 전 원본 응답 선택 보관 |
| `database/evaluation/` | 검색 평가 질문, 기대 문서와 평가 결과 관리 |
| `database/scripts/` | 수집·정규화·적재·청킹·임베딩·평가 실행 |
| `database/.env.example` | 안전한 환경변수 예시 제공 |
| `database/requirements.txt` | DB 데이터 처리용 Python 의존성 관리 |
| `database/README.md` | 전체 실행 순서와 사용 방법 설명 |

## 5. `database/`에 두지 않는 코드

- 사용자 요청마다 실행되는 MCP Tool
- Agent의 Tool 선택 정책
- 사용자용 LLM 답변 생성
- Frontend 화면과 Backend Router
- Redis 최근 대화 문맥 및 검색 캐시 처리
- Repository의 실시간 검색 SQL 구현

`database/`는 DB와 데이터를 **준비·갱신·검증하는 영역**이다. 실제 서비스 요청의 검색 흐름은 `legal_mcp/services`와 `legal_mcp/repositories`가 담당한다.

## 7. 명명 이유

- `migrations`: DB를 이전 구조에서 다음 구조로 변경하는 이력
- `seeds`: 빈 DB에 심는 검증된 초기 데이터
- `raw`: 외부에서 받은 가공 전 원본
- `evaluation`: 검색 품질 평가 질문과 결과
- `scripts`: 서버 요청 코드가 아닌 독립 실행형 데이터 작업
- `collect`: 외부 데이터 수집 단계
- `normalize`: 서로 다른 데이터를 공통 형식으로 통일하는 단계
- `ingest`: 검증된 데이터를 실제 DB에 적재하는 단계
- `chunk_and_embed`: 검색 단위 분할과 Vector 생성 단계
- `evaluate_retrieval`: LLM 답변이 아닌 검색 결과 품질 평가 단계

핵심은 이름만 보고도 **데이터가 어느 단계에 있고 어떤 작업이 책임지는지 설명할 수 있도록 하는 것**이다.
