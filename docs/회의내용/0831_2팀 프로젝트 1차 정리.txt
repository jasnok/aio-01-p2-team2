지금까지 전체 채팅과 방금 정리한 `legal_ai_agent_architect`, 그리고 강사님 강조사항까지 합치면 **프로젝트 방향은 상당히 명확해졌어.**

## 1. 현재 프로젝트 주제

### **법률 사례 검색 AI Agent**

단순한 **"법률 상담 AI"**가 아니라,

> **사용자가 자신의 법률 문제 상황을 자연어로 입력하면, Agent가 관련 법령과 유사 사례를 검색하고 근거·출처와 함께 정리해주는 서비스**

로 잡는 게 현재 팀의 방향이야.

예를 들어:

> "중고거래를 했는데 돈을 입금했는데 판매자가 물건을 보내지 않고 연락도 안 됩니다."

라고 입력하면,

```text
사용자 질문
   ↓
Legal AI Agent
   ↓
질문 유형/카테고리 판단
   ↓
법령 검색 Tool
   ↓
판례/사례 검색 Tool
   ↓
PostgreSQL + pgvector
   ↓
관련 자료 검색
   ↓
LLM이 검색 결과 정리
   ↓
관련 법령 + 유사 사례 + 출처 + 주의사항
```

을 보여주는 구조야.

---

# 2. 왜 "법률 전체"가 아니라 사례 검색으로 좁혔나?

처음에는

* 부동산 법률
* 범죄 사례
* 다양한 법률 검색
* 법률 상담

등을 생각했지만, **3일짜리 4인 프로젝트**라는 조건 때문에 범위를 줄였어.

법률 전체를 다루면 데이터와 Agent가 너무 커지기 때문에,

### 1차 MVP

**"일상생활에서 발생하는 법률 문제 → 관련 법령 + 유사 사례 검색"**

정도로 잡는 게 적절해.

그리고 카테고리를 버튼으로 제한하는 방식.

예:

```text
[중고거래]
[임대차]
[근로]
[교통]
[소비자 분쟁]
```

사용자가 카테고리를 선택하고 질문을 입력하도록 하면 검색 범위를 통제할 수 있어.

# 3. 프로젝트에서 가장 중요한 부분

이번 프로젝트는 **프론트 디자인이나 단순 CRUD가 핵심이 아님.**

강사님이 강조한 부분을 보면 핵심은:

### **Agent + Tool + MCP + RAG + DB를 어떻게 설계하고 연결했는가**

야.

특히 다음 구조가 중요해.

```text
                 ┌─ search_laws
                 │
User → Backend → Agent → Tool → MCP Server
                 │                  │
                 │                  ├─ 법령 API
                 │                  ├─ 판례 API
                 │                  └─ DB
                 │
                 └─ 필요한 Tool 선택
                            ↓
                    PostgreSQL + pgvector
                            ↓
                       검색 결과
                            ↓
                           LLM
                            ↓
                  근거 기반 답변
```

---

# 4. RAG와 Agent의 역할을 명확하게 구분

이번 프로젝트에서 이 부분을 발표할 때 상당히 중요해.

### RAG

**"자료를 찾는 역할"**

```text
질문
 ↓
Embedding
 ↓
Vector Search
 ↓
관련 법률 자료
```

### Agent

**"무엇을 검색할지 판단하는 역할"**

예를 들어:

```text
사용자 질문
 ↓
Agent
 ↓
법령만 검색하면 될까?
 ├─ YES → search_laws
 │
 └─ NO
      ↓
   판례도 필요한가?
      ↓
   search_cases
```

즉,

> **RAG는 검색 방법이고 Agent는 검색 전략을 결정하는 주체**

라는 구조로 설명할 수 있어.

---

# 5. DB는 PostgreSQL + pgvector

DB는 단순히 데이터를 저장하는 용도로 끝내지 않고 **RAG의 핵심 인프라**로 사용.

### 법령 데이터

```text
법령명
조문번호
조문제목
조문내용
시행일
출처
embedding
```

### 판례 데이터

```text
사건번호
법원
선고일
사건명
판결요지
판결내용
출처
embedding
```

---

## SQL과 Vector Search도 구분

이 부분도 프로젝트에서 보여주면 좋아.

### 정확한 질문

> "근로기준법 제36조 알려줘."

→ SQL/Keyword Search

### 의미 기반 질문

> "퇴사했는데 회사에서 월급과 퇴직금을 안 줘요."

→ Vector Search

### 복합 질문

> "이런 상황에서 실제로 비슷한 판례가 있었나요?"

→

**Agent + SQL + Vector Search**

즉 최종적으로는 **Hybrid Search** 구조를 가져가는 게 좋음.

---

# 6. MCP Server는 외부 데이터와 DB를 연결하는 핵심

추천 Tool은 현재 이렇게 정리할 수 있어.

| Tool                     | 역할          |
| ------------------------ | ----------- |
| `search_laws`            | 관련 법령 검색    |
| `get_law_article`        | 특정 법령/조문 조회 |
| `search_cases`           | 유사 판례/사례 검색 |
| `get_case_detail`        | 특정 사례 상세 조회 |
| `search_legal_documents` | 법률자료 통합 검색  |

다만 **3일 프로젝트이므로 전부 구현할 필요는 없어.**

### MVP

```text
search_laws
search_cases
get_law_article
```

정도로 시작하고 시간이 남으면 확장.

---

# 7. 외부 API + 자체 DB를 같이 사용하는 방향

지금까지 이야기했던 **외부 API/MCP를 활용할 것인가, 직접 데이터를 구축할 것인가**도 이렇게 정리하면 좋아.

### 외부 데이터

* 법령 API
* 판례 API
* 기타 법률 데이터

### 자체 DB

```text
PostgreSQL
   +
pgvector
```

에 프로젝트에서 필요한 데이터를 저장.

즉,

> **외부 API에서 원천 데이터를 가져오고 → 필요한 데이터를 PostgreSQL에 저장 → Embedding → pgvector → RAG 검색**

이라는 구조를 만들 수 있어.

이게 단순히 "API 호출해서 결과 보여주는 프로젝트"보다 훨씬 프로젝트다운 구조가 돼.

---

# 8. Redis는 실제 기능으로 활용

강사님이 캐싱을 강조했으므로 Redis도 그냥 설치만 하면 안 돼.

### 활용 예시 ① 단기 대화

사용자가

> "중고거래 사기 관련 사례를 찾아줘."

라고 한 다음

> "그중에서 피해자가 돈을 돌려받은 사례만 보여줘."

라고 하면 이전 질문을 기억해야 함.

```text
질문 1
 ↓
Redis
 ↓
질문 2
 ↓
Agent
 ↓
이전 Context 고려
```

### 활용 예시 ② 검색 캐시

동일하거나 유사한 검색이 반복되면 Redis에 결과를 캐싱.

```text
질문
 ↓
Redis Cache 확인
 ├─ 있음 → 즉시 반환
 │
 └─ 없음
      ↓
   Agent → MCP → DB/API
      ↓
   결과
      ↓
   Redis 저장
```

강사님이 말한 **네이버 자동완성 / 회사 내규 / FAQ 검색**과 같은 캐싱 활용을 법률 검색에 연결하는 거야.

# 9. LLM은 모든 것을 판단하는 것이 아님

```text

 ↓
LLM
 ↓
법률 답변
```

이렇게 하면 환각(Hallucination) 위험이 커.

### ⭕

```text
사용자 질문
 ↓
Agent
 ↓
Tool
 ↓
MCP
 ↓
DB / API
 ↓
실제 법률 근거
 ↓
LLM
 ↓
정리
```

즉,

> **검색은 DB/API/MCP가 담당하고 LLM은 검색된 자료를 이해하기 쉽게 정리한다.**

# 11. Front / Backend / MCP / DB를 분리

```text

     │
     ↓

     │
     ↓

     │
```

# 🎯 결국 지금 우리 프로젝트를 한 문장으로 정리하면

> **"사용자가 일상적인 법률 문제 상황을 입력하면 AI Agent가 적절한 법령·판례 검색 Tool을 선택하고, MCP Server를 통해 PostgreSQL + pgvector 및 외부 법률 데이터를 검색한 뒤, LLM이 검색된 근거와 출처를 바탕으로 유사 사례와 법률 정보를 정리해주는 법률 정보 검색 서비스"**

이게 지금까지 회의 + 강사님 요구사항 + 우리가 앞서 논의한 내용까지 합친 **현재 프로젝트의 가장 정확한 정의**라고 보면 돼.

### 🔥 개발 우선순위도 한 줄로 압축하면

**DB/RAG → MCP/Tool → Agent → Backend → Frontend → Redis/SSE/Login/Admin → 부가 기능**

이고,

**"기능을 많이 넣는 것"보다 "왜 이렇게 Agent·Tool·MCP·RAG·DB를 나눴고 어떻게 연결했는가"를 보여주는 프로젝트**로 가는 게 이번 3일 프로젝트에서는 가장 중요해.
