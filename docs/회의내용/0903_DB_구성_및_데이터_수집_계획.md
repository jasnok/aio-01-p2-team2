# 법률 사례 검색 AI Agent --- DB 구성 및 데이터 수집 계획

## 1. 전체 방향

`3차_plan.md` 기준으로 DB는 **원문 문서 저장 영역**과 **RAG 검색용
Chunk/Embedding 영역**을 분리해서 구성한다.

``` text
공식 데이터 소스
  ├─ 국가법령정보 공동활용 - 법령 API
  └─ 국가법령정보 공동활용 - 판례 API
              ↓
        데이터 수집 스크립트
              ↓
          Raw JSON/XML
              ↓
            정규화
              ↓
      PostgreSQL 원문 테이블
              ↓
          Chunking
              ↓
          Embedding
              ↓
        pgvector 저장
              ↓
          MCP Server
              ↓
            Agent
```

국가법령정보 공동활용을 중심으로 판례 목록/본문과 법령 목록/본문
데이터를 수집하고, 이를 팀의 공통 Schema로 정규화한 뒤 PostgreSQL +
pgvector에 저장한다.

## 2. DB 기본 구성

우선 다음 3개 테이블을 사용한다.

``` text
legal_documents
→ 법령/판례 원문과 메타데이터

legal_chunks
→ RAG 검색용 Chunk + Embedding

ingestion_runs
→ 데이터 수집 기록
```

### 2.1 `legal_documents`

``` sql
CREATE TABLE legal_documents (
    id BIGSERIAL PRIMARY KEY,
    external_id VARCHAR(100) UNIQUE,
    document_type VARCHAR(20) NOT NULL,
    category VARCHAR(20),
    title TEXT NOT NULL,
    law_name TEXT,
    article_number VARCHAR(50),
    case_number VARCHAR(100),
    case_name TEXT,
    court VARCHAR(100),
    decided_at DATE,
    judgment_result TEXT,
    summary TEXT,
    content TEXT NOT NULL,
    source_name TEXT NOT NULL,
    source_url TEXT,
    effective_date DATE,
    metadata JSONB,
    content_hash VARCHAR(64),
    collected_at TIMESTAMP DEFAULT NOW(),
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

`document_type`은 `LAW`, `CASE`, `GUIDELINE`으로 시작한다. 판례의 경우
`case_number`, `case_name`, `court`, `decided_at`, `judgment_result`,
`source_url` 등을 저장한다.

### 2.2 `legal_chunks`

RAG 검색 전용 테이블이다.

``` sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE legal_chunks (
    id BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL
        REFERENCES legal_documents(id)
        ON DELETE CASCADE,
    chunk_index INTEGER NOT NULL,
    content TEXT NOT NULL,
    token_count INTEGER,
    embedding vector(1536),
    embedding_model VARCHAR(100),
    embedding_version VARCHAR(50),
    created_at TIMESTAMP DEFAULT NOW(),
    UNIQUE(document_id, chunk_index)
);
```

`vector(1536)`은 예시이며 실제 사용하는 Embedding Model의 차원에 맞춰
확정한다.

### 2.3 `ingestion_runs`

데이터 수집 상태를 관리하기 위한 테이블이다.

``` sql
CREATE TABLE ingestion_runs (
    id BIGSERIAL PRIMARY KEY,
    source_name VARCHAR(100) NOT NULL,
    document_type VARCHAR(20),
    started_at TIMESTAMP DEFAULT NOW(),
    finished_at TIMESTAMP,
    status VARCHAR(20),
    fetched_count INTEGER DEFAULT 0,
    inserted_count INTEGER DEFAULT 0,
    updated_count INTEGER DEFAULT 0,
    failed_count INTEGER DEFAULT 0,
    error_message TEXT
);
```

이를 통해 오늘 판례 몇 건을 가져왔는지, 어디에서 실패했는지, 몇 건이
신규 저장·갱신되었는지를 관리할 수 있다.

## 4. 판례 데이터 수집

``` text
query="퇴직금"
 ↓
판례 목록 API
 ↓
판례 일련번호 목록
 ↓
각 ID로 판례 본문 API 호출
 ↓
Raw 데이터 저장
 ↓
정규화
 ↓
legal_documents 저장
```

개념적인 Python 구조:

``` python
def collect_cases(keyword: str):
    page = 1

    while True:
        items = fetch_case_list(
            query=keyword,
            page=page,
            display=100,
        )

        if not items:
            break

        for item in items:
            detail = fetch_case_detail(item["판례일련번호"])
            save_case(detail)

        page += 1
```

판례 목록에서 판례 일련번호를 확보한 뒤 해당 ID를 사용해 판례 본문을
가져온다.

## 5. 법령 데이터 수집

법령은 판례처럼 대량으로 수집하기보다 각 카테고리에 필요한 핵심 법령부터
가져온다.

### Housing

-   주택임대차보호법
-   민법

### Labor

-   근로기준법
-   근로자퇴직급여 보장법

### Consumer

-   전자상거래법
-   소비자기본법
-   민법

국가법령정보 공동활용의 법령 목록/본문 API를 통해 필요한 법령과 조문을
수집하고 DB에 저장한다.

## 6. API 데이터 정규화

외부 API의 Response 구조를 그대로 DB와 MCP에서 사용하지 않는다.

``` text
API Response
 ↓
normalize
 ↓
공통 Schema
 ↓
PostgreSQL
```

판례 정규화 결과 예시:

``` python
{
    "external_id": "228541",
    "document_type": "CASE",
    "category": "labor",
    "title": "...",
    "case_number": "...",
    "case_name": "...",
    "court": "...",
    "decided_at": "...",
    "judgment_result": "...",
    "summary": "...",
    "content": "...",
    "source_name": "국가법령정보센터",
    "source_url": "..."
}
```

이렇게 하면 MCP Server는 외부 Open API의 실제 Response Schema에 직접
의존하지 않고 `legal_documents`의 공통 Schema만 사용하면 된다.

## 7. Category 분류

Open API가 `housing`, `labor`, `consumer` 카테고리를 직접 제공하지 않는
경우 팀에서 분류한다. MVP 단계에서는 수집에 사용한 검색어를 기준으로
카테고리를 부여할 수 있다.

``` python
KEYWORD_CATEGORY = {
    "보증금 반환": "housing",
    "임대차": "housing",
    "퇴직금": "labor",
    "부당해고": "labor",
    "중고거래": "consumer",
    "환불": "consumer",
}
```

향후 하나의 판례가 여러 카테고리에 해당해야 한다면 관계 테이블을
추가하는 방식으로 확장할 수 있다. MVP에서는 단일 `category`로 시작한다.

## 8. Chunking

법령과 판례는 서로 다른 방식으로 Chunking한다.

### 8.1 법령

법령은 **조문 단위**를 우선한다.

``` text
주택임대차보호법 제3조 → Chunk 1
주택임대차보호법 제3조의2 → Chunk 2
주택임대차보호법 제4조 → Chunk 3
```

기본적으로 `조문 하나 = Chunk 하나`로 구성하고, 너무 긴 조문만 추가
분리한다.

### 8.2 판례

판례는 의미 구조를 최대한 유지한다.

``` text
사건 정보
판시사항
판결요지
사실관계
법원의 판단
결론 / 판결 결과
```

단순히 일정 글자 수마다 자르기보다 의미 있는 섹션을 기준으로 나눈다.

초기 기준:

``` text
500~800 tokens
overlap 50~100 tokens
```

## 9. Embedding 데이터 구성

Embedding에는 Chunk 본문만 넣지 않고 검색에 필요한 Metadata를 함께
포함한다.

``` text
문서유형: 판례
카테고리: 임대차·주거
사건명: 임대차보증금
사건번호: XXXX다XXXXX
법원: 대법원

핵심 내용:
임대차 종료 후 보증금 반환 의무...
```

이 문자열을 Embedding Model에 전달해 Vector를 생성하고
`legal_chunks.embedding`에 저장한다.

## 10. Hybrid Search

검색은 Vector Search와 Keyword/SQL Search를 결합한다.

``` text
Vector Search 70%
Keyword Search 30%
```

자연어 사례는 pgvector similarity 중심으로 검색하고, 정확한
법령·조문·사건번호는 SQL/Keyword Search를 우선한다.

``` text
자연어 사례
→ pgvector

정확한 법령/사건번호
→ SQL/Keyword

복합 검색
→ Hybrid Search
```

검색 결과에서는 동일 문서의 중복 Chunk를 제거하고 임계값 미달 결과를
제외한 뒤 Top 3를 반환한다.

## 14. 핵심 개발 전략

Open API부터 구현하지 않는다.

먼저 다음 흐름을 완성한다.

``` text
Mock Data
 ↓
PostgreSQL
 ↓
Chunking
 ↓
Embedding
 ↓
pgvector
 ↓
MCP Server
```

이 흐름이 정상 동작하면 Mock Data 입력 부분만 실제 Open API 데이터
수집으로 교체한다.

``` text
Open API
 ↓
Raw
 ↓
Normalize
 ↓
PostgreSQL
 ↓
Chunking / Embedding
 ↓
pgvector
 ↓
MCP Server
```

이 방식을 사용하면 외부 API 문제 때문에 전체 프로젝트 개발이 중단되는
위험을 줄일 수 있다.

## 15. 최종 역할 정리

``` text
국가법령정보 공동활용
= 공식 법령/판례 데이터 원천

Raw Data
= API에서 수집한 원본 보관

Normalize
= 외부 API 구조를 팀 공통 Schema로 변환

legal_documents
= 법령/판례 원문 및 Metadata 저장

legal_chunks
= RAG 검색용 Chunk 및 Vector 저장

pgvector
= 사용자 사례와 의미적으로 유사한 자료 검색

MCP Server
= DB/RAG 검색 기능을 Tool 형태로 Agent에 제공

Agent
= 사용자의 질문에 따라 필요한 MCP Tool 선택

LLM
= 검색된 공식 근거를 기반으로 사용자에게 설명
```

최종적으로 DB/RAG 계층의 목표는 **공식 법률 데이터를 안정적으로
수집·정규화·저장하고, 사용자의 자연어 사례와 의미적으로 유사한 법령 및
판례를 검색할 수 있는 기반을 제공하는 것**이다.
