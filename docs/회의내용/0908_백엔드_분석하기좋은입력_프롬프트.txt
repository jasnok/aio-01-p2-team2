좋습니다. 구체성 판단은 Backend Agent의 ‘입력 검증’ 단계로 옮기고, Frontend는 판단 결과와 보완 질문만 표시하면 됩니다. 프로젝트 가이드의 ‘필수값 확인 → 보완 질문’에도 맞습니다.
다만 지금의 네 가지 기준을 그대로 Agent에게 적용하기보다, 사용자가 원하는 답변에 필요한 정보가 있는지 판단하도록 바꾸는 것을 추천합니다.
- “퇴직금 관련 법 조문을 알려주세요” → 구체적인 날짜 없이도 검색 가능
- “제가 받을 퇴직금을 계산해주세요” → 근무기간·임금 정보 등이 필요
- “일시불 결제 후 할부 전환한 경우 할부항변권을 행사할 수 있나요?” → 이미 쟁점이 구체적이므로 검색 진행
즉, 모든 질문에서 날짜·상대방·증거를 필수로 요구하면 안 됩니다.
추천 동작은 다음과 같습니다.
사례 분석하기 클릭
→ Backend Agent가 질문 목적·정보 충분성 판단
   ├─ 검색 가능 → MCP 검색 → 답변
   └─ 필수 정보 부족 → 보완 질문 반환
→ Frontend가 Backend 결과 표시
입력할 때마다 LLM을 호출하면 비용과 지연이 발생하므로, 버튼을 누른 뒤 판단하는 방식이 현재 일정에 적절합니다.
Backend와 합의할 응답 예시는 다음과 같습니다. 아직 구현된 계약은 아닌 제안입니다.
{
  "input_assessment": {
    "decision": "needs_clarification",
    "message": "퇴직금 계산에 필요한 정보가 부족합니다.",
    "missing_information": [
      "근무기간",
      "임금 정보"
    ],
    "clarifying_questions": [
      "입사일과 퇴사일을 알려주세요.",
      "퇴직 전 임금 정보를 알려주세요."
    ]
  }
}
검색 가능한 경우에는 다음처럼 기존 분석 결과와 함께 반환합니다.
{
  "input_assessment": {
    "decision": "ready",
    "message": "질문에 필요한 정보가 있어 관련 자료를 검색했습니다.",
    "missing_information": [],
    "clarifying_questions": []
  }
}
needs_clarification 응답을 기존의 “분석 완료”로 처리하지 않도록 최상위 상태와 필수 응답 필드도 함께 합의해야 합니다.

프론트엔드에서는 기존 “2/4점” 표시를 없애고, Backend가 보낸 안내 문장과 필요한 정보만 보여주는 것이 좋습니다. 아직 판단하지 않았거나 Backend 호출이 실패했다면, “정보가 부족하다”고 임의로 표시하지 않아야 합니다.
