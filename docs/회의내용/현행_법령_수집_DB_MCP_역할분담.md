# 현행 법령 수집: DB 담당자와 MCP 서버 담당자의 역할 분담

## 질문

> 문서와 현재 작업 비교 라인에서 전부 다 작업해야 하는 거잖아?  
> 그러면 현행 법령 수집은 DB 담당자인 내가 하는 건가, 아니면 MCP 서버 담당자가 해야 하는 건가? 동시에 해야 하는 건가?

## 결론

**두 담당자가 동시에 진행하되, 책임 범위를 나누는 방식이 가장 적절합니다.**

- **DB 담당자**는 서비스가 반복적으로 검색할 법령 데이터를 수집·정제하고 PostgreSQL 및 pgvector에 적재합니다.
- **MCP 서버 담당자**는 최신성 확인이나 DB에 없는 내용을 외부 법령 API에서 조회하는 기능을 구현합니다.
- 동일한 데이터를 양쪽에서 각각 따로 관리하는 것이 아니라, **DB를 기본 검색원으로 사용하고 외부 API를 보완 수단으로 사용**합니다.

즉, 현행 법령 수집을 MCP 담당자에게 전부 넘기는 것도 아니고, DB 담당자가 외부 API 서비스까지 전부 구현하는 것도 아닙니다.


## DB 담당자의 작업 범위

DB 담당자는 다음 작업을 맡는 것이 좋습니다.

1. **수집 대상 법령 확정**
   - 부동산·주택 임대차
   - 노동법
   - 소비자·중고거래

2. **원본 데이터 확보**
   - 파일 데이터가 있으면 파일을 우선 사용
   - 파일로 부족한 법령은 공식 API를 이용해 수집 가능
   - API는 수집 수단일 뿐이며, 수집 결과는 원본 파일로도 보관

3. **정규화 및 적재**
   - 법령명, 법령 ID, 조문 번호, 조문 제목, 본문
   - 시행일, 공포일, 출처, 원본 URL, 수집 시각
   - PostgreSQL의 문서·조문·청크 테이블에 저장

4. **RAG 데이터 구성**
   - 조문 단위 또는 의미 단위로 청크 생성
   - `text-embedding-3-small`로 임베딩
   - pgvector 컬럼에 저장
   - 임베딩 모델명과 차원을 메타데이터로 기록

5. **데이터 검증**
   - 중복 여부
   - 필수 필드 누락 여부
   - 조문 수와 청크 수
   - 임베딩 누락 여부
   - 대표 질문의 유사도 검색 결과

6. **재수집 기준 제공**
   - 법령 개정 여부를 비교할 식별자와 시행일 저장
   - 추후 갱신 작업이 가능하도록 수집 스크립트와 실행 방법 정리

DB 담당자가 법령 API를 한 번 호출하여 데이터를 받아 적재하는 것은 자연스러운 업무 범위입니다. 다만 사용자 요청 때마다 API를 호출하는 실시간 연동 서버까지 DB 담당자가 맡을 필요는 없습니다.

## MCP 서버 담당자의 작업 범위

MCP 서버 담당자는 다음 작업을 맡는 것이 좋습니다.

1. **외부 법령 API 연동 도구 구현**
   - 법령명 또는 키워드 검색
   - 법령·조문 상세 조회
   - 시행일 및 현행 여부 확인

2. **DB 검색 결과가 부족할 때 보완 조회**
   - 검색 결과가 없을 때
   - 관련도가 기준값보다 낮을 때
   - 최신 개정 여부를 확인해야 할 때

3. **응답 형식 통일**
   - DB 결과와 외부 API 결과를 서비스가 같은 방식으로 처리할 수 있도록 공통 JSON 계약 사용

4. **장애 및 제한 대응**
   - 타임아웃
   - 호출 실패
   - 호출 횟수 제한
   - 재시도 및 오류 메시지

5. **출처 표시**
   - 법령명, 조문, 시행일, 공식 출처 URL을 최종 답변에 전달

## 함께 먼저 정해야 할 공통 계약

동시 작업을 시작하기 전에 아래 항목은 두 담당자가 합의해야 합니다.

### 공통 데이터 필드 예시

```json
{
  "source_type": "statute",
  "source_provider": "국가법령정보센터",
  "external_id": "법령의 공식 식별자",
  "title": "전자상거래 등에서의 소비자보호에 관한 법률",
  "article_no": "제17조",
  "article_title": "청약철회등",
  "content": "조문 본문",
  "effective_date": "YYYY-MM-DD",
  "source_url": "공식 출처 URL",
  "retrieved_at": "수집 시각",
  "category": "consumer"
}
```

### 추가로 합의할 항목

- 법령과 판례의 고유키 생성 규칙
- 카테고리 값: `housing`, `labor`, `consumer`
- 조문 및 판례 청크 기준
- DB 검색 결과가 부족하다고 판단하는 기준
- 외부 API 호출 조건
- 최신성 판단 기준
- DB 결과와 외부 API 결과가 충돌할 때의 우선순위

## 동시에 작업하는 방법

두 담당자는 다음 순서로 병렬 진행할 수 있습니다.

| 단계 | DB 담당자                 | MCP 서버 담당자               |
| ---- | ------------------------- | ----------------------------- |
| 1    | 테이블 및 공통 필드 검토  | 외부 API 응답 구조 확인       |
| 2    | 샘플 법령 수집·정규화     | 샘플 API 호출 도구 구현       |
| 3    | 청크·임베딩·pgvector 적재 | 공통 JSON 형식으로 변환       |
| 4    | 대표 질문 검색 검증       | DB 부족 시 API 호출 조건 구현 |
| 5    | 적재 결과와 출처 제공     | DB 검색과 외부 조회 결과 통합 |

중요한 점은 **공통 JSON 계약을 먼저 고정한 다음 동시에 작업하는 것**입니다. 이 계약 없이 각자 구현하면 필드명, 식별자, 날짜 형식과 출처 표현이 달라져 통합 단계에서 문제가 생깁니다.

## 3일 미니 프로젝트에서의 현실적인 범위

### 반드시 완료할 부분

- 핵심 법령을 PostgreSQL에 저장
- 검색용 청크 및 pgvector 임베딩 생성
- 대표 질문 3개에 대한 검색 결과 검증
- MCP 서버에서 최소한의 법령 검색 또는 상세 조회 지원
- DB 우선, 외부 API 보완이라는 동작 원칙 정의
- 모든 결과에 출처와 기준일 표시

### 후순위로 둘 수 있는 부분

- 모든 법령의 자동 개정 감지
- 대규모 정기 동기화 배치
- 복잡한 캐시 무효화
- 외부 API 장애에 대한 고급 재시도 정책
- 전체 법령 및 판례 수집

## Redis와 캐시의 위치

Redis는 법령 원본의 영구 저장소가 아닙니다.

- PostgreSQL: 법령·판례 원문과 메타데이터 영구 저장
- pgvector: 법령·판례 청크의 의미 검색
- Redis: 반복 검색 결과, 외부 API 응답, 최근 대화 이력 캐시
- 최근 대화 이력: 기존 합의대로 **24시간, 최대 20개**

외부 법령 API 응답은 짧은 TTL로 캐시할 수 있지만, 검증된 데이터를 장기적으로 활용하려면 정규화 과정을 거쳐 PostgreSQL에 적재해야 합니다.
