# 분석 자동 저장과 완료 후 저장의 동일 실행 키

## 문제와 변경

실행 작업의 자동 저장은 답변의 request_id를 사용했지만 완료 후 저장 API는 run_id를
사용했다. DB의 source_request_id 멱등 키가 달라 동일 결과가 별도 대화로 저장될 수 있었다.
자동 저장에서 run_id를 명시적으로 전달하여 두 경로를 통일했다. 독립 응답 API의 저장은
기존 request_id 기본값을 유지하며 API 응답의 request_id도 변경하지 않는다.

## 검증

- 실제 실행 함수에 합성 답변을 주입하여 자동 저장과 후속 저장 두 번의 실행 키가
  모두 run_id인지 확인한다. 모델 호출이나 유료 API는 사용하지 않는다.
- 실제 PostgreSQL에서 기존 저장소의 INSERT/ON CONFLICT를 실행하여 대화 1건,
  사용자·답변 메시지 각 1건, 동일 conversation_id 반환을 확인한다.
- 같은 키를 다른 회원으로 저장하려 하면 거부되고 기존 소유자·메시지가 유지된다.
- 기존 독립 응답 저장의 request_id 계약 테스트도 유지한다.

PostgreSQL 테스트는 RUN_POSTGRES_INTEGRATION을 명시할 때만 실행한다. 연결의
search_path를 pg_temp로 제한하고 임시 테이블만 생성하며 연결 종료로 정리한다.
실제 사용자 테이블이나 데이터를 수정하지 않는다. 임시 테이블은 이 테스트에 필요한
컬럼·멱등 unique 제약만 제공하므로 전체 운영 스키마·외래키 검증을 대신하지 않는다.
CI는 별도 PostgreSQL 16 서비스에서 이 테스트를 실행한다.

## 적용 범위

새 코드로 실행되는 분석의 저장 키를 바로잡는다. 이미 서로 다른 키로 저장된 기존
이력은 삭제·강제 병합하거나 마이그레이션하지 않는다. 배포 이전에 자동 저장된 실행을
새 코드에서 완료 후 저장하면 이전 키와 차이가 남을 수 있다. DB와 Redis 사이의 원자적
분산 트랜잭션이나 모델 exactly-once 실행을 보장하는 변경도 아니다.
