# AI 포트폴리오 3차 구현과 운영 배포 계획

이 문서는 1~4단계의 구현 범위와 검증 한계, 5~6단계의 작업 순서와 완료 기준을 정리합니다. 품질 평가를 재현하고, 검색 근거와 답변의 관계를 추적하며, 운영 장애를 설명할 수 있는 AI 시스템이 목표입니다. 작업 브랜치는 `codex/portfolio-optimize-v2`이며 이번 요청은 새 PR 병합이나 실제 공개 배포를 포함하지 않습니다.

## 1단계 평가 데이터와 실험 계약

합성 질문 60건을 `tests/portfolio_quality_dataset.py`에 정의했습니다. 식별자 조회 15건, 기존 자연어 15건, 예외 조건·혼동 사례·자료 범위 부족·불명확 입력·지시문 공격 30건입니다. 식별자 외의 관련성 정답과 기대 행동은 사람 검토 대기 상태입니다. 자동 생성한 질문을 사람 정답으로 취급하지 않습니다.

개발용과 보류 평가용을 사례 유형별로 분리하고 버전을 고정했습니다. 이는 초기 구분이며 동일 법적 쟁점이 두 구분에 걸쳐 있을 수 있습니다. 최종 평가 전에 사람이 쟁점 그룹을 다시 검토하고, 중복 표현·동일 쟁점 누출을 제거해야 합니다. 현재 보류 세트는 엄밀한 독립 시험 세트로 발표할 수 없습니다.

검색 비교 도구는 `--dataset quality --split development|holdout`를 지원합니다. 후보 재평가 도구는 기존 세 방식의 후보 청크를 합쳐 모델이 순서를 선택하도록 하고, 누락·중복·없는 후보 ID를 거부합니다. 평가 후보를 넓히는 전체 DB 검색 실험과는 다릅니다. 현재 3개 질문을 실행했고 순위 개선 여부는 사람 채점 전입니다. 모델 순위를 관련성 정답으로 저장하지 않습니다.

`scripts/evaluate_context.py`는 문서와 청크 원문, 추출 구절, 정확한 위치, 원문 해시를 보관합니다. 기존 검색 결과 268개 청크의 구절 위치 검사는 오류 0건, 빈 문맥 0건이었습니다. 문서와 청크의 의미 관련성, 압축 후 예외 조건 보존 여부는 별도 채점해야 합니다. 기존 HTML 검토표의 후보 통합 문서 평가와 이 청크 검토 파일은 구분해서 사용합니다.

### 사람이 채점할 기준

| 대상 | 기록할 항목 | 해석 |
|---|---|---|
| 문서 | 관련성 0~3, 판단 이유 | 질문과 자료 주제의 일치 |
| 청크 | 관련성 0~3, 필요한 주변 문맥 | 같은 문서의 청크 선택 성능 |
| 추출 구절 | 조건·예외 누락 여부 | 압축의 의미 손실 |
| 주장 | 지지·부분 지지·근거 없음 | 인용과 주장의 관계 |
| 보류 | 적절·과도·필요했으나 미실행 | 근거 부족 대응 |

채점자와 자료 버전을 기록하고 일부 표본은 두 사람이 독립 채점해 불일치를 합의합니다. nDCG·Precision은 미검토 항목을 0점으로 채우지 않습니다. Recall은 정답 근거 후보를 충분히 조사한 질문에만 계산합니다.

## 2단계 원문 문맥 보존

기존 280자 분할을 문장 경계·주변 문장·연속된 예외 구절을 보존하는 선택 방식으로 교체했습니다. 각 구절은 원문 시작·끝 위치, SHA256, 선택 알고리즘 버전을 갖습니다. 구절 ID도 원문 해시와 위치를 포함합니다. 문서당 최대 2,400자 문맥을 선택하며 예산에 맞추려고 문장을 자르지 않습니다. 길이가 지나치게 큰 분할 불가능 본문은 인용 문맥에서 제외될 수 있습니다.

현재 변경은 답변용 문맥 추출에 적용됩니다. DB의 2,797개 임베딩 청크를 법령 조·항, 판례 판시사항·판결요지, 상담 질문·답변 단위로 다시 적재한 것은 아닙니다. 이를 위해서는 원본 정규화와 새로운 임베딩 버전의 병렬 적재가 필요합니다. 기존 검색 인덱스를 덮어쓰지 않고 별도 버전에서 품질을 비교한 뒤 전환하는 후속 작업으로 남깁니다. 시행일·최신성은 원본 메타데이터가 확인된 경우에만 채웁니다.

## 3단계 주장 의미 검토와 제한된 수정

`AnswerReview` 계약은 모든 주장 번호를 정확히 한 번 포함하고 supported·partial·unsupported로 판정합니다. 숫자·대상·기한·예외가 다르면 전체 지지로 보지 않도록 지시합니다. 입력은 주장과 실제 인용 원문이며 외부 사실을 보충하지 않습니다.

문제 있는 주장은 전체 답변 생성 입력에 해당 판정만 피드백하여 최대 한 번 다시 생성합니다. 이는 잘못된 주장만 대상으로 한 개별 패치 API가 아니라 피드백을 제한한 전체 구조화 재생성입니다. 재검토 후에도 미지지 주장은 제외하고, 지지 주장이 없거나 검토 자체가 실패하면 대체 답변으로 종료합니다. 모델 판정은 의미 검토 보조 결과이지 법률 정답·최신성 보장이 아닙니다.

`SEMANTIC_VERIFICATION_ENABLED=true`가 기본이며 `false`로 원문 존재 검사만 하는 기준선과 비교할 수 있습니다. `ANSWER_REPAIR_ATTEMPTS`는 0 또는 1입니다. 검토·재생성은 추가 비용과 대기 시간을 발생시키므로 품질 채점 후 기본 정책을 재결정합니다.

## 4단계 단계별 모델과 성능 기록

`INTAKE_MODEL`, `ANSWER_MODEL`, `VERIFICATION_MODEL`을 따로 설정하고 비워 두면 `OPENAI_MODEL`을 사용합니다. 실제 모델을 더 작은 모델로 바꾸는 실험은 아직 수행하지 않았습니다. 입력 의미 판단을 단순 키워드 규칙으로 대체하지 않았습니다.

요청별로 입력 판단·답변 생성·수정·검토의 호출 모델, 알려진 토큰 사용량과 SDK 반환 시간을 기록합니다. `ContextVar`로 요청별 호출 기록을 분리합니다. 반환 전에 시간 초과된 호출과 임베딩 토큰은 합계에 포함되지 않으며 이 범위를 diagnostics에 명시합니다. 따라서 전체 청구 비용이라고 발표하지 않습니다. 임베딩 사용량과 요금표에 따른 금액 환산은 후속 계측 대상입니다.

`scripts/benchmark_analysis.py`는 4개 실제 API 시나리오를 지정한 횟수만큼 반복하고 커밋·작업 트리 상태·질문 버전·모델 호출 기록을 남깁니다. 캐시 상태는 운영자가 선언하므로 자동으로 냉각·예열을 보장하지 않습니다. 최소 20개 성공 표본 전에는 p95를 표시하지 않습니다. 여러 분야와 보완 안내를 섞은 전체 요약만으로 분야별 지연 성능을 주장하지 않습니다. 동시 사용자 부하 실험은 아직 포함하지 않습니다.

### 재현 명령

```powershell
./scripts/test_all.ps1
.venv/Scripts/python -X utf8 scripts/evaluate_context.py
.venv/Scripts/python -X utf8 scripts/compare_reranking.py --model gpt-5-mini --limit 3
.venv/Scripts/python -X utf8 scripts/benchmark_analysis.py --repeats 1
```

실제 모델 호출 명령은 API 비용을 발생시킵니다. 검색 비교의 60건 전부 실행은 별도 시간·비용을 고려해 수행하며, 이미 보류 평가 데이터를 열어 튜닝한 경우 새 보류 세트를 구성합니다.

### 이번 실제 검증 결과

최종 전체 회귀 테스트는 278개 통과·4개 제외입니다. 요청별 계측 분리 테스트도 포함합니다. 실제 API 4건은 주거·근로·소비자 생성 3건과 보완 안내 1건이며 중복 요청·소유자 분리·SSE·원문 인용 검사는 모두 통과했습니다.

단일 실행 시간은 주거 33.719초, 근로 34.032초, 소비자 62.187초, 정보 부족 7.406초입니다. 소비자는 생성·검토·수정·재검토를 거쳤으며 재검토에서 부분 지지로 판정된 주장 하나를 제외했습니다. 나머지 두 주장으로 답변을 구성했습니다. 이는 모델의 보조 판정이며 사람이 의미를 검증한 것은 아닙니다. 검증 추가로 시간이 증가할 수 있음을 보여주는 기록이며 속도 개선률로 발표하지 않습니다. 4개 표본이므로 p95는 산출하지 않았습니다.

원본은 `output/phase3/benchmark/`에, 후보 재평가 3건은 `output/phase3/reranking.json`에 보관했습니다. DB 전체 재청킹과 60건 검색 평가, 여러 모델·반복 설정의 품질 비교는 아직 실행하지 않았습니다.

## 5단계 실행 안정화 세부 계획

예상 작업량은 단독 개발 3~5일이며 아래 순서로 작은 PR을 나눕니다.

### 5A 상태 저장의 원자적 전이

- 실행 스냅샷에 revision·attempt·worker_id·lease_expires_at을 추가합니다.
- Redis Lua로 기대 revision·상태·작업 소유권이 맞을 때만 전이합니다.
- 조회 시 중단 판정을 최신 스냅샷과 비교하고 완료 결과 덮어쓰기를 방지합니다.
- 완료·실패는 최종 상태이며 오래된 Worker가 되돌릴 수 없게 합니다.
- 완료 기준: 동시에 실패 판정과 완료 저장을 실행해도 최종 완료가 유실되지 않는 경합 테스트 통과.

### 5B API와 Worker 분리

- API는 입력 계약 확인과 원자적 예약·큐 등록 후 run_id를 반환합니다.
- Redis Streams consumer group을 사용하는 Worker 서비스 하나부터 추가합니다.
- 예약과 큐 등록은 같은 원자적 작업으로 수행해 예약만 남는 작업을 방지합니다.
- 소비자는 처리 후 ACK하고, lease가 만료된 미완료 작업은 회수합니다.
- 전달은 최소 한 번일 수 있으므로 Worker의 attempt와 lease로 결과 저장 중복을 방지합니다. 외부 LLM 호출의 정확히 한 번 실행은 보장하지 않습니다.
- 완료 기준: API 재시작과 Worker 종료 후 미완료 작업이 설정된 회수 시간 안에 다시 처리되며 결과 저장은 한 번 유지.

### 5C 비용 제한과 재시도

- Worker 동시 실행 수·큐 길이·소유자별 요청 한도를 설정합니다.
- 429·일시 연결 장애만 지수 지연으로 제한 재시도하고 형식·인용 실패는 무한 재시도하지 않습니다.
- 단계별 완료 결과를 체크포인트로 저장해 재실행 시 유효한 검색 결과를 재사용합니다.
- 시도 한도 초과 작업은 실패 큐로 분리하고 사용자에게 재요청 안내를 제공합니다.
- 완료 기준: 부하 증가 시 요청이 무제한 쌓이지 않고 대기·거부·실패 원인이 구분됨.

### 5D 장애와 부하 검증

- 입력 판단·검색·생성 단계마다 Worker를 강제 종료합니다.
- Redis 중단, LLM 시간 초과, 같은 요청 키의 동시 요청, SSE 재연결을 주입합니다.
- 합성 질문으로 동시 사용자 1·5·10명을 비교하고 큐 대기·처리·실패율을 분리합니다.
- 결과 산출물: 장애 표, 단계별 복구 시간, 중복 저장 검사, 요청당 알려진 사용량.
- 종료 조건: lease 경합·중복 결과·끝나지 않는 polling이 없고, 처리 실패가 정의한 terminal 상태로 끝남.

## 6단계 배포와 포트폴리오 세부 계획

예상 작업량은 단독 개발 3~5일입니다. 공개 배포 전에 5단계 검증을 완료합니다.

### 6A 재현 가능한 CI

- Mock 단위 테스트와 Postgres·Redis·MCP를 사용하는 합성 통합 테스트를 분리합니다.
- 실제 모델 평가는 수동 실행·요청 수 제한으로 운영하고 키 없는 PR에서는 실행하지 않습니다.
- 이미지와 의존성을 버전 고정하고 커밋 태그 이미지, 데이터 버전, 평가 버전을 함께 보관합니다.
- 완료 기준: 빈 환경에서 seed 복원·서비스 시작·대표 검색·SSE 종료가 CI에서 통과.

### 6B 배포 구성

- 우선 한 대의 서버에서 Compose와 HTTPS reverse proxy로 배포합니다. 서버 사양과 비용은 실제 환경 선택 후 확정합니다.
- 외부에는 웹 진입점만 노출하고 API·MCP·Postgres·Redis는 내부 네트워크로 연결합니다.
- 공개 데모에는 임의 guest_id를 인증 수단으로 쓰는 현재 흐름을 그대로 사용하지 않습니다. 서버 발급 데모 세션·요청 제한·예산 한도를 적용합니다.
- 키는 런타임 secret으로 주입하고 사용자 질문을 운영 로그에 남기지 않는 정책을 점검합니다.
- DB·Redis 백업과 복원 리허설, 이전 이미지 태그 롤백 절차를 작성합니다.
- 완료 기준: 별도 PC에서 HTTPS 접속, 제한 초과 안내, 이전 버전 롤백, 백업 복원 검증.

### 6C 평가와 운영 결과 화면

- 합성 데모 데이터로 검색 방식·문맥·검증 사용 여부를 비교하는 별도 평가 화면을 만듭니다.
- 실험마다 요청 수·데이터 버전·캐시 상태·실패 표본을 표시합니다.
- 모델 내부 추론을 노출하지 않고 인용·단계 시간·검증 상태만 보여줍니다.
- 현재 시스템이 결정적 검색 오케스트레이션이라는 점을 명시하고 자율 다중 Agent 시스템으로 과장하지 않습니다.
