# LawPath 팀 합의 요청사항

> **클릭해서 합의할 곳:** [GitHub Issue #19 - 개발·통합 기준 최종 확인](https://github.com/jasnok/aio-01-p2-team2/issues/19)
>
> 이 문서는 합의할 내용을 빠르게 이해하기 위한 요약본이다. 실제 체크, 수정 의견, 최종 합의는 위 GitHub Issue에서 진행한다.

## 합의하는 방법

1. 위 GitHub Issue를 연다.
2. 자신이 담당하는 항목의 설명을 확인한다.
3. 동의하면 체크박스를 클릭한다.
4. 수정이 필요하거나 궁금한 점이 있으면 해당 항목을 체크하지 않고 댓글을 남긴다.
5. 의견이 해결되고 담당자 확인란이 모두 체크되면 **항목 최종 합의**를 체크한다.
6. 모든 항목과 마지막 **팀 프로젝트 개발 기준 최종 합의 완료**가 체크되면 전체 합의가 끝난다.

일부 담당자만 체크한 항목은 아직 합의된 것으로 보지 않는다.

## 현재 프로젝트 구성

```text
사용자
→ Frontend
→ Backend API
→ AI Agent
→ MCP 검색 도구
→ PostgreSQL
→ 검색·분석 결과를 Frontend에 표시
```

- Frontend: 사용자 화면과 입력·결과 표시
- Backend: 요청, 로그인, 권한, Agent 실행 관리
- Agent: 질문에 맞는 법률 분야와 Tool 선택
- MCP: 법령과 판례 검색
- PostgreSQL: 법률 자료와 영속 이력 보관
- Redis: 로그인 Session, 짧은 대화 문맥, Agent 진행 상태 임시 보관

## Frontend 보완 추천

현재 Mock Frontend에는 홈, 3개 법률 분야, 사례 분석, 법령·판례 검색, FAQ·질문 게시판, 질의 이력, 관리자, 페이지 이동, QA 화면이 구현되어 있다. 기존 기능을 다시 만들기보다 다음 순서로 보완하는 것을 추천한다.

1. 분석 진행 단계 표시와 처리 중 버튼 비활성화
2. 검색 결과 없음, 근거 부족, 서버 연결 실패, 시간 초과 등의 Mock 오류 화면
3. 답변 문장과 관련 법령·판례·공식 출처 연결
4. 이전 분석에 이어 묻는 후속 질문과 새 분석 시작
5. 예상 결과와 실제 결과를 비교하는 Agent 평가 화면
6. 작은 화면, 접힌 사이드바, 키보드 조작 등 반응형·접근성 점검

Frontend에서 화면은 먼저 구현할 수 있지만 진행 상태 이름, 오류 코드, 근거 필드, 대화 ID는 Backend 담당자와 합의해야 한다.

## 팀 프로젝트 우선 합의 추천

### 1. 첫 통합 기능

다음 한 경로를 먼저 완성한다.

```text
퇴직금 대표 질문
→ LaborAgent
→ MCP 판례 검색
→ PostgreSQL·pgvector 검색
→ 유사 판례 Top 3
→ Frontend 표시
```

이 경로가 정상 작동한 뒤 임대차와 소비자 분야에 같은 구조를 적용한다.

### 2. 호출 순서

```text
Frontend는 Backend만 호출
Backend는 Agent와 MCP 호출
MCP는 PostgreSQL 검색
```

Frontend가 MCP나 DB에 직접 접속하지 않는 방식을 추천한다.

### 3. 공통 계약

- API, MCP Tool, DB 필드 이름을 명세서 기준으로 통일한다.
- 전체 팀이 같은 대표 질문과 Mock JSON을 사용한다.
- 정상 응답뿐 아니라 오류 응답과 **근거 없음** 상태도 확정한다.
- 계약 변경은 관련 코드와 명세서를 같은 PR에서 수정한다.

### 4. 근거와 검색 결과

- 국가법령정보센터와 법원 등 확인 가능한 공식 출처를 우선 사용한다.
- 판례 Top 3에는 사건번호, 법원, 선고일, 관련도, 출처를 포함한다.
- 관련도는 승소 가능성이 아니라는 안내를 표시한다.
- 근거가 부족하면 억지로 결과를 채우지 않고 **NO_EVIDENCE**를 반환한다.

### 5. 실행 상태와 중복 방지

- Agent 진행 상태를 Redis에 기록한다.
- Backend가 SSE로 진행 상태를 Frontend에 전달한다.
- Frontend는 처리 중 버튼을 비활성화한다.
- Backend는 **Idempotency-Key**로 같은 요청의 중복 실행을 막는다.

### 6. 로그인과 데이터 보관

- 로그인은 Backend Session과 HttpOnly Cookie 사용을 우선 추천한다.
- 짧은 대화 문맥과 실행 상태는 Redis에 임시 보관한다.
- 회원 질의 이력과 공개 질문은 PostgreSQL에 영속 보관한다.
- 비회원 질의 이력은 7일 보관안을 우선 제안한다.
- 관리자만 공지 FAQ 관리와 사용자 질문 답변을 할 수 있게 한다.

### 7. 팀 통합 방식

- 공통 명세, 환경설정, DB Migration 수정 전 팀 채팅에 알린다.
- 큰 PR 하나보다 기능 단위의 작은 PR을 만든다.
- 수업일 오전·오후에 대표 질문으로 통합 상태를 확인한다.
- 오류가 나면 Frontend → Backend → MCP → DB 순서로 실패 구간을 확인한다.
