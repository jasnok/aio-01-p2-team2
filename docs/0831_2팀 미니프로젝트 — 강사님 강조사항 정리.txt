# 📌 2팀 미니프로젝트 — 강사님 강조사항 정리

팀원들과 공유하기 쉽게 **강사님이 강조하신 내용 + 프로젝트에서 종합적으로 고려할 기술 요소**만 정리했습니다.

---

## 1. 🏗️ 전체 시스템 구조를 먼저 설계

이번 프로젝트는 기능부터 만드는 것보다 **전체적인 System Architecture를 먼저 잡는 것**이 중요.

종합적으로 다음 구성요소를 고려:

* Frontend
* Backend
* Login
* User / Admin
* SSE
* Redis
* Database
* LLM
* AI Agent
* Tool
* MCP Server
* Multimodal (MOV, MP3 등)
* 서버 간 통신 구조

> **각 구성요소의 역할과 연결 관계가 명확하게 보이는 구조로 설계**

---

## 2. 🤖 AI Agent + Tool + MCP Server 설계가 가장 중요

강사님이 **이번 프로젝트에서 가장 중요하다고 강조한 부분.**

단순히 Agent, Tool, MCP를 각각 구현하는 것이 아니라,

> **Agent가 어떤 상황에서 어떤 Tool을 사용하고, 어떤 경우에 MCP Server를 호출할 것인지**

를 먼저 기획해야 함.

```text
User
 ↓
AI Agent
 ↓
판단
 ↓
Tool 선택
 ↓
MCP Server / DB / API
 ↓
결과 수집
 ↓
LLM
 ↓
Response
```

---

## 3. 📁 폴더 구조는 "의도"가 명확해야 함

폴더를 단순히 기능별로 나누는 것이 아니라,

> **왜 이렇게 나눴는지 설명할 수 있는 구조**

로 구성.

예:

```text
frontend/
backend/
mcp/
database/
```

각 폴더가 어떤 책임을 가지고 있는지 명확하게 해야 함.

**디렉터리 구조 자체가 System Architecture와 연결되도록 설계.**

---

## 4. 🗄️ DB는 Supabase + Docker 모두 고려

DB 환경을 하나에 고정하지 않고,

```text
.env
 ↓
DB 설정 변경
 ↓
Supabase
또는
Docker PostgreSQL
```

처럼 **환경변수 변경만으로 DB를 교체해서 사용할 수 있도록 구성.**

---

## 5. 🔐 환경변수 관리

환경에 따라 달라지는 값이나 민감한 정보는 코드에 직접 작성하지 않고 `.env`로 분리.

예:

```text
DATABASE_URL
REDIS_URL
LLM_API_KEY
SUPABASE_URL
SUPABASE_KEY
MCP_SERVER_URL
```

Frontend와 Backend의 환경변수도 **각각 필요한 것만 별도로 관리**.

---

## 6. 🧠 LLM은 "생성"보다 "정리"에 활용

LLM이 모든 정보를 직접 생성하도록 하기보다,

```text
실제 데이터
   ↓
DB / Vector DB / API / MCP
   ↓
검색 결과
   ↓
LLM
   ↓
정리 / 요약 / 자연어 응답
```

형태로 활용.

> **검색과 데이터 조회는 DB/API가 담당하고, LLM은 결과를 이해하기 쉽게 정리하는 역할**

---

## 7. 💾 Redis — 캐싱 + 단기 대화내역

Redis를 단순히 설치하는 것이 목적이 아니라 **실제 활용처를 만들어야 함.**

### 단기 대화

```text
사용자 질문
 ↓
대화 내용 저장
 ↓
후속 질문
 ↓
이전 대화 Context 활용
```

### 캐싱

강사님 예시:

* 네이버 자동완성
* 회사 내규 검색
* FAQ 게시판

즉,

> **반복적으로 사용되는 데이터나 단기 대화 Context를 Redis에 저장해 성능과 사용자 경험을 개선**

---

## 8. 🛠️ Tool Description은 상세하게

Agent가 Tool을 정확하게 선택할 수 있도록 **Tool Description을 구체적으로 작성.**

Tool마다 최소한:

* 무엇을 하는 Tool인지
* 어떤 데이터를 반환하는지
* 언제 사용해야 하는지
* 어떤 입력값이 필요한지

등을 명확하게 정의.

> **Agent가 Description만 보고 적절한 Tool을 선택할 수 있도록 작성**

---

## 9. 🔘 카테고리는 어느 정도 버튼화

사용자가 모든 것을 자유롭게 입력하도록 하면 서비스 범위가 너무 커질 수 있음.

따라서 핵심 카테고리는 UI에서 어느 정도 선택하도록 구성.

예:

```text
[카테고리 A]
[카테고리 B]
[카테고리 C]
[카테고리 D]
```

그 안에서 사용자가 상세 내용을 입력하도록 설계.

→ 검색 범위 제한
→ 검색 정확도 향상
→ 데이터 관리 용이

---

## 10. 📡 SSE 고려

AI Agent 처리 과정이나 응답 시간이 긴 작업은 **SSE(Server-Sent Events)**를 활용해 실시간으로 상태를 전달.

예:

```text
🔍 질문 분석 중...
      ↓
📚 데이터 검색 중...
      ↓
🤖 Agent 처리 중...
      ↓
📝 답변 정리 중...
      ↓
✅ 완료
```

사용자가 기다리는 동안 현재 처리 상태를 보여줄 수 있도록 설계.

---

## 11. 👤 Login / User / Admin

기본적인 사용자와 관리자 역할을 구분.

### User

* 로그인
* 서비스 이용
* 검색
* 검색 결과 확인
* 검색 이력 등

### Admin

* 데이터 관리
* 사용자 관리
* 사례/콘텐츠 관리
* 서비스 상태 확인 등

**단, 3일 프로젝트이므로 실제 구현 범위는 프로젝트 주제에 맞게 최소화.**

---

## 12. 🎥 Multimodal도 가능성 고려

MOV, MP3 등 멀티모달 입력도 **전체 설계 단계에서는 고려.**

예:

```text
MP3
 ↓
음성 → Text
 ↓
AI Agent
```

또는

```text
MOV
 ↓
음성/텍스트 추출
 ↓
AI Agent
```

다만 **핵심 기능을 완성한 후 시간이 남을 경우 확장하는 영역**으로 보는 것이 좋음.

---

# ⭐ 강사님 강조사항 핵심 요약

### 가장 중요한 순서로 보면

**① System Architecture**

→ 전체 구조를 먼저 설계

**② AI Agent + Tool + MCP**

→ Agent가 무엇을 판단하고 어떤 Tool/MCP를 사용할지 기획

**③ DB / RAG / LLM**

→ 실제 데이터를 검색하고 LLM은 검색 결과를 정리

**④ Redis / Cache**

→ 반복 데이터와 단기 대화 Context 활용

**⑤ 명확한 폴더 구조**

→ 각 구성요소의 책임과 의도가 보이게 구성

**⑥ 환경변수 관리**

→ DB/API/LLM/MCP 등의 설정을 `.env`로 분리

**⑦ Front / Back / SSE / Login / Admin**

→ 서비스 형태를 완성하는 기본 기능

**⑧ Multimodal**

→ 시간과 주제에 따라 확장 기능으로 고려

---

### 🎯 한 문장으로 정리

> **이번 프로젝트는 단순히 기능을 많이 만드는 것이 아니라, Frontend–Backend–DB–LLM–Agent–Tool–MCP–Redis가 어떤 역할을 가지고 어떻게 연결되는지를 명확하게 설계하고 구현하는 것이 핵심.**
