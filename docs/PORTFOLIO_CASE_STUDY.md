# LawPath 개인 개선: 설계 선택과 시연

## 담당 범위

4인 팀 프로젝트에서 장상옥은 프론트엔드 화면과 API 연결을 담당했습니다. 백엔드·AI Agent는 임다혁, MCP 검색은 오병훈, DB·데이터는 박지혜의 팀 기여입니다. 이후 개인 개선은 이 저장소의 Issue·PR과 아래 문서로 구분하여 설명합니다. 팀 전체 구현을 개인 성과로 표현하지 않습니다.

## 면접에서 설명할 세 가지 설계 선택

| 문제 | 선택과 구현 | 검증 근거 | 남은 한계 |
|---|---|---|---|
| 생성 답변의 근거를 확인하기 어려움 | 주장별 인용 ID·원문 구절을 검사하고 검증 실패를 대체 답변으로 표시 | [평가·주장 검증](PORTFOLIO_PHASE3_AND_ROADMAP.md), [MCP 응답 계약](MCP_SEARCH_CONTRACT.md) | 원문 존재 검사는 법적 타당성이나 주장 전체의 함의를 보장하지 않음 |
| 재조회·중복 접수·연결 장애가 실행 상태를 혼동시킴 | Redis 원자적 예약·버전 검사, 회원/게스트 소유자 분리, SSE 입력 검증, 명시적 재시도에서 요청 키 유지 | [실행 상태](RUN_STATE_CONTRACT.md), [소유자 분리](ACTOR_RESULT_ISOLATION.md), [HTTP 장애](FRONTEND_HTTP_FAILURES.md) | 모델 호출의 정확히 한 번 실행·과금 취소 보장 없음. 내구성 큐와 중단 작업 자동 재개 없음 |
| 검색 부속 작업의 반복 초기화 비용 | 임베딩 SDK 클라이언트 수명주기 관리, 키워드별 SQL을 한 DB 연결에서 실행 | [클라이언트 재사용](EMBEDDING_CLIENT_REUSE.md), [DB 연결 재사용](KEYWORD_CONNECTION_REUSE.md), [측정 출처](BENCHMARK_PROVENANCE.md) | SQL 횟수는 동일. 결과 동등성과 해당 단계 시간만 확인했으며 전체 상담 지연·검색 품질 개선으로 해석하지 않음 |

구조를 바꿀 때 작업 큐나 새 에이전트 프레임워크를 먼저 추가하지 않았습니다. 현재 프로세스의 실행 수는 [접수 제한](RUN_ADMISSION_CONTROL.md)으로 제한하고, 공유 연결은 [종료 수명주기](SHARED_CLIENT_LIFECYCLE.md)로 정리했습니다. 다중 프로세스 전체 실행 한도와 내구성 작업 실행은 별도 과제입니다.

## 수치와 근거를 읽는 방법

발표 화면은 [숫자 요약 JSON](../frontend/data/portfolio-evidence.json)을 읽습니다. 원본과의 일치는 `python scripts/build_portfolio_evidence.py --check`로 검증합니다. 원본을 다시 측정한 명령이 아니며 새 API 요청을 보내지 않습니다.

- [SDK 생성 비용 v2](../output/portfolio/embedding-client-acquisition-v2.json): 준비 5회 후 15개 표본. 생성 중앙값 약 399.75ms, 재사용 획득 약 0.0019ms. 가짜 키로 SDK 객체 생성만 측정했고 모델 요청은 하지 않았습니다.
- [키워드 DB 조회 v2](../output/portfolio/keyword-connections-v2.json): 범주별 준비 2쌍·측정 10쌍. 주거 324.72→151.08ms, 노동 259.93→91.16ms, 소비자 485.01→316.53ms. 범주별 준비 포함 12쌍 결과가 동일했습니다. 각 입력의 연결 수는 5→1이며 벡터 검색·LLM 시간은 포함하지 않습니다.
- 측정 당시 Git HEAD뿐 아니라 작업 트리 변경 여부와 관련 코드 해시를 함께 기록합니다. DB 문서 수·청크 수와 선언된 데이터 버전은 고정 DB 스냅샷을 뜻하지 않습니다. 자세한 계약은 [측정 출처 문서](BENCHMARK_PROVENANCE.md)를 참고합니다.
- 자연어 검색 관련성은 [사람 검토 입력 계약](RETRIEVAL_REVIEW_CONTRACT.md)을 준비한 상태입니다. 사람 라벨과 품질 향상 수치는 아직 없습니다.

## 약 3분 시연 준비와 촬영

1. [로컬 실행 안내](DOCKER_LOCAL_SETUP.md)에 따라 기존 환경 파일을 보존하면서 Docker 서비스를 실행합니다. `frontend/.env`의 `FRONTEND_PRESENTATION_MODE=true` 설정을 적용한 후 프론트엔드를 재생성합니다. 접속 주소는 `http://localhost:8501`입니다.
2. 리허설에서 분석 완료·실패 안내를 확인하고 촬영할 질문을 선택합니다. 실제 분석은 API 비용이 들며 같은 답변을 보장하지 않습니다. 측정 화면 열기에는 모델 호출이 없습니다.
3. 다음 순서로 녹화합니다. 실제 대기 시간을 편집하면 자막으로 표시하고, 키·토큰·개인 상담 내용은 녹화에 포함하지 않습니다.

| 시간 | 화면과 설명 |
|---|---|
| 0:00–0:20 | README 담당 범위: 팀 프론트엔드와 개인 개선을 구분 |
| 0:20–1:10 | 질문 입력과 진행 상태: 검색·답변 단계가 화면에 전달되는 과정 |
| 1:10–1:45 | 답변·근거 원문: 인용 확인과 검증 한계. 실패 결과는 실패로 설명 |
| 1:45–2:10 | 정보 부족 질문: 보완 질문을 받는 흐름 |
| 2:10–2:30 | PDF·이력: 저장·다운로드 기능과 소유자 분리 |
| 2:30–3:00 | 발표 패널의 엔지니어링 측정 결과: 범위 선택, 표본 수·출처·한계 설명 |

발표 패널의 데모 준비 버튼도 분석을 호출하므로 리허설·촬영 횟수를 고려합니다. 이 문서는 촬영 절차이며 공개된 영상이나 배포 사이트가 이미 있다는 의미는 아닙니다.
