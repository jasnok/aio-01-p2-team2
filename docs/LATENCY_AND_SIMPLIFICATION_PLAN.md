# 응답 속도 개선과 코드 단순화 계획

main에 병합한 검색 최적화와 근거 검증을 기준으로, 다음 작업은 직렬 모델 호출 시간과 재생성 비용을 줄이는 데 집중합니다. 검증을 통과한 주장만 답변에 표시하는 계약을 유지하고, 기능을 바꾸는 실험과 코드 구조 정리를 작은 PR로 나눕니다. 아래는 작업 기준이며 구현·실험 현황은 [응답 속도 실험과 코드 리팩토링 결과](LATENCY_REFACTOR_REPORT.md)에 기록합니다. 기본 설정 변경을 위한 사람 채점과 충분한 반복은 남아 있습니다.

## 현재 기록과 병목

기준 구현은 PR #85의 main 병합 커밋 `2d4e837`입니다. 측정은 병합 전 동일 기능의 작업 트리에서 수행한 `output/phase3/benchmark/summary.json`이며 데이터에는 당시 커밋과 dirty 상태가 기록돼 있습니다. 단일 실행·통제하지 않은 캐시 상태이므로 대표 성능이나 개선율로 해석하지 않습니다.

상담 3건에서 알려진 모델 호출 시간의 합은 전체의 약 95~98%입니다. 이는 이번 표본의 관측입니다. 검색 쿼리를 더 빠르게 만드는 것만으로 큰 전체 시간 감소를 기대하기 어렵다는 것이 현재 가설입니다. 첫 근거 표시 시간과 최종 검증 답변 시간은 따로 측정해야 합니다.

## 실행 순서와 완료 기준

### 1 측정 기준부터 바로잡기

대상은 `scripts/benchmark_analysis.py`, `scripts/portfolio_smoke.py`, `backend/app/services/model_metrics.py`, `legal_question_service.py`입니다.

- 모델의 단일 호출 시간과 전체 생성·검토 구간을 각각 기록합니다. 현재 `generation_ms`는 재생성 시 마지막 생성 호출 시간으로 덮어써질 수 있습니다.
- 입력 판단·검색·문맥 구성·생성·검토·재생성·전체 시간을 분리하고, 호출 횟수·재생성률·제외 주장 수·fallback 비율을 기록합니다.
- SSE를 요청 시작부터 수신해 첫 근거와 최종 답변 도착 시간을 기록합니다. 기존 종료 후 SSE 재생 검사는 유지하되 실시간 지연과 구분합니다.
- `completed`·`stopped`·`fallback`·실패를 별도 집계합니다. 계약 검사가 실패하면 벤치마크 명령도 실패 종료하고 표본은 보존합니다.
- 캐시 상태를 단순한 사용자 선언에서 실제 제어·확인 가능한 실험 조건으로 바꿉니다. 개인정보가 포함된 질문이나 대화 내용을 운영 계측에 남기지 않습니다.
- 반복 결과의 원본은 한 번만 저장하고 요약은 실행 파일 경로와 집계만 담습니다. 현재 summary에 전체 samples를 다시 포함하는 중복을 줄입니다.

완료 기준은 합성 지연을 넣은 테스트에서 구간 시간이 올바르게 구분되고, 실패 표본이 빠지지 않는 것입니다. 모델 호출 없이 계측 계약을 먼저 검증합니다.

### 2 재생성 없는 검증 경로 비교

이미 있는 `ANSWER_REPAIR_ATTEMPTS=0`을 실험 조건으로 사용합니다. 검토는 유지하며 supported 주장만 남깁니다. 모두 제거되면 기존 fallback으로 전환하고 지지 범위를 사용자에게 표시합니다.

- 같은 개발 질문에서 현재 1회 재생성 경로와 0회 경로를 비교합니다.
- 비교 항목은 응답 시간뿐 아니라 질문에 대한 답변 충족도, 최종 주장 수, 근거 없는 주장, fallback 비율입니다.
- 소비자 표본의 재생성·재검토 25.213초는 줄일 수 있는 구간이지만, 다른 초안이 생성될 수 있어 이 값을 실제 개선 시간으로 약속하지 않습니다.
- 사람이 확인한 품질 기준을 만족할 때만 기본값 변경을 제안합니다. 기본값 변경 전까지 기존 동작을 유지합니다.

완료 기준은 지원되지 않는 주장이 최종 답변에 포함되지 않고, 응답 범위 축소와 속도 이득을 함께 보고하는 것입니다. 재생성이 여전히 필요하면 전체 답변을 다시 생성하는 대신 실패 주장만 고치는 후속 실험을 진행합니다. 부분 수정은 주장 인덱스·인용 ID 검증과 재검토를 포함하며 처음부터 구현하지 않습니다.

### 3 단계별 모델과 출력량 비교

이미 분리한 `INTAKE_MODEL`, `ANSWER_MODEL`, `VERIFICATION_MODEL`을 사용합니다. 후보 모델의 지원 기능과 비용은 구현 시 공식 문서와 실제 호출로 확인합니다. 특정 모델이 빠르다는 가정을 기본 설정에 바로 반영하지 않습니다.

- 입력 판단과 검토부터 후보 하나씩 비교하고 답변 생성 모델은 별도로 비교합니다.
- 단계별 출력 길이와 지원되는 추론·출력 설정을 검토합니다. 현재 usage의 output_tokens는 사용자에게 보이는 문장 길이와 같다고 가정하지 않습니다.
- status·checks·claim_index·verdict 등 계약 필드는 유지하고 판정 이유와 반복 안내의 길이만 제한하는 실험을 합니다.
- 입력 판단의 형식 재시도와 SDK 네트워크 재시도를 합쳐 최대 호출 횟수와 시간 예산을 명시합니다. 재시도는 오류 종류에 따라 구분합니다.

완료 기준은 입력 충분성 오판과 검토 오류를 사람이 확인하고, 같은 질문에서 시간·알려진 사용량·품질을 비교하는 것입니다. 검토 모델의 supported 판정 자체를 정답으로 채점하지 않습니다.

### 4 연결 재사용과 비동기 호출 정리

현재 OpenAIProvider는 호출마다 client를 만들고 입력 판단·생성·검토는 동기 호출을 `asyncio.to_thread`로 실행합니다. 취소가 발생해도 실행 중인 스레드 호출은 계속될 수 있습니다.

- 앱 시작·종료 수명주기에 맞춰 클라이언트와 연결을 재사용하고, 현재 SDK가 지원하는 비동기 호출로 요청 경로를 통일합니다.
- 공통 호출 함수에서 단계 시간 예산·계측·오류 분류를 처리합니다. 모델 옵션은 요청별로 전달해 여러 Provider 객체 생성과 분기를 줄입니다.
- CLI 평가 도구의 동기 호출은 얇은 별도 경계로 유지하고 API 내부에서 실행 중인 이벤트 루프를 다시 시작하지 않습니다.
- 취소가 상위 실행에서 전달되는지 검증합니다. 취소가 서버 측 모델 처리나 청구 취소를 보장한다고 설명하지 않습니다.

완료 기준은 동시 요청의 계측 분리, 시간 초과, 연결 종료, 한 요청의 취소가 다른 요청에 영향을 주지 않는 테스트입니다. 단일 요청의 모델 추론 시간이 크게 줄어드는 변경으로 기대하지 않고 연결·동시 처리 비용 개선으로 측정합니다.

### 5 문맥과 검토 입력의 중복 줄이기

- 재생성 여부와 관계없이 `build_context`는 요청당 한 번만 호출하고, 동일한 documents·spans를 재사용합니다.
- 현재 최대 6개 문서·문서당 3개 구절을 기준으로 작은 후보 구성을 비교합니다. 질문 전체에 필요한 조건·예외·자료 유형을 보존하고 문장 중간을 잘라 토큰 수를 맞추지 않습니다.
- 같은 인용문을 여러 주장이 사용하면 검토 입력에 span 사전을 한 번 넣고 주장에는 ID만 전달하는 방식과 현재 원문 반복 방식을 비교합니다.
- 문서·구절을 무조건 줄이지 않고 사람 채점에서 관련성·충족도·예외 누락이 악화되는 구성은 제외합니다.

완료 기준은 원문 오프셋·해시 검증과 입력 토큰 감소를 확인하고, 예외 조건·숫자·기한을 가진 사례에서 의미 손실을 검토하는 것입니다.

### 6 답변 서비스의 흐름을 읽기 쉽게 분리

`answer_with_llm`의 재귀 재생성과 큰 try 블록을 다음의 명시적인 흐름으로 바꿉니다.

`문맥 준비 → 초안 생성 → 인용 검증 → 의미 검토 → 선택적 수정 → 최종 주장 선택 → 응답 조립`

- `AnswerContext`에 documents·spans를 담고 순수 함수로 인용 검증과 최종 주장 선택을 분리합니다.
- 초기 생성 1회와 선택적 수정 최대 1회를 명시적인 반복문으로 표현합니다. 수정 시에도 동일한 문맥을 사용합니다.
- typed 결과에 draft·generation_status·fallback_reason·검토 이력을 담습니다. 실제 사용한 호출 수와 최종 성공 여부를 구분합니다. 현재 `state.llm_calls = int(llm_used)`는 실제 총 호출 수가 아닙니다.
- 요청별 계측 컨텍스트의 set/reset을 한곳에 모으고, 서비스 내부의 가변 diagnostics 딕셔너리 전달을 줄입니다.
- 현재 quotes 모드는 호환 테스트와 외부 사용 여부를 확인한 뒤 제거 또는 경계 어댑터로 분리합니다. 사용 여부를 확인하지 않고 삭제하지 않습니다.
- 동작을 보존하는 구조 변경과 모델·기본값 변경을 같은 PR에 섞지 않습니다. 범용 Agent 프레임워크나 새 저장소 계층을 추가하지 않습니다.

완료 기준은 기존 API·SSE·인용 계약이 유지되고, unknown span·부분 지지·지원 주장 없음·검토 형식 오류·취소의 각 경로를 짧은 테스트로 설명할 수 있는 것입니다. 함수 줄 수만 줄이기 위해 검증을 합치지 않습니다.

## 실험 규칙과 잠정 목표

개발 세트에서 먼저 소규모 비교를 진행합니다. 선택한 두 구성만 쟁점 중복을 다시 검토한 보류 세트에서 비교하고, 보류 세트 결과를 보고 설정을 계속 튜닝하지 않습니다. API 실험은 케이스 수·반복 수·최대 호출 수를 사전에 제한합니다. 60건 전부와 모든 조합을 바로 실행하지 않습니다.

한 설정만 바꾼 짝 비교를 번갈아 실행하고 모델·프롬프트·문맥·데이터·캐시·커밋 버전을 고정합니다. 같은 조건에서 상담 사례별 20개 이상의 성공 표본을 확보하기 전 p95를 대표 지표로 사용하지 않습니다. 20개도 안정성을 보장하는 기준은 아니므로 표본 수와 분포를 함께 보고합니다. 실패·fallback은 성공 시간 통계 밖에서도 전체 요청 분모로 반드시 표시합니다.

잠정 개발 목표는 검토를 포함한 일반 상담 중앙값 25초 이내와 긴 재생성 사례 축소입니다. 이는 달성 결과나 서비스 보장이 아닙니다. 현재 3건과 섞어 개선율을 계산하지 않고 새 기준 실험에서 비교합니다. 속도보다 먼저 원문 인용 일치, 미지지 주장 제외, 소유자 분리, 추가 질문 계약을 유지합니다. 답변 충족도와 검토 오판의 허용 기준은 사람 채점 기준표에 정의한 뒤 기본값을 바꿉니다.
