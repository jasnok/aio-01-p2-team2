# 응답 속도 실험과 코드 리팩토링 결과

응답 시간 계측, 비동기 호출·연결 재사용, 답변 검증 흐름 단순화를 구현했습니다. 재생성 횟수·단계별 모델·추론량·문맥 크기·검토 입력 중복을 비교하는 도구와 빠른 시연 설정도 추가했습니다. 빠른 설정의 실제 API 상담 2건은 23.687초와 18.094초였지만, 사람의 품질 채점과 충분한 반복 측정이 남아 있어 기본 설정은 유지합니다.

## 구현 범위

| 계획 | 적용한 내용 | 남은 확인 |
| --- | --- | --- |
| 1 측정 | 실시간 SSE의 첫 근거·종료 시간, 단계별 호출·사용량·실패 집계, 종료 후 검사 시간 분리, 원본 파일 참조 요약 | 설정별 반복과 동시 부하 |
| 2 재생성 | 0회·1회 비교, 지원 주장만 유지하는 경로와 한도 테스트 | 사람 채점 후 기본값 결정 |
| 3 모델·출력량 | 단계별 모델·추론량 설정, 같은 질문의 단계별 비교 도구 | 더 큰 개발 세트와 독립 평가, 출력 길이 제약의 추가 실험 |
| 4 연결 | 요청별 새 client 생성 대신 루프별 AsyncOpenAI 재사용, 앱 종료 시 close, 공통 비동기 호출·취소·계측 | 실제 서비스의 동시 사용자 부하 |
| 5 문맥 | 요청당 문맥 1회 구성, 문서·구절·문자 예산 설정, 동일 검토 인용의 사전 공유 실험 | 예외·범위 손실에 대한 사람 채점 |
| 6 구조 | 재귀 제거, typed 결과, 인용 검증·지원 주장 선택의 순수 함수 분리 | quotes 호환 모드는 유지, 제거 여부 별도 확인 |

`legal_question_service.py`는 생성과 최대 1회 수정을 명시적인 반복문으로 실행합니다. `answer_contract.py`에 문맥·결과 타입과 인용·최종 주장 규칙을 모았습니다. 원문 정규화도 인용마다 반복하지 않고 자료별로 한 번 수행합니다. 공개 `answer_with_llm` 함수는 기존 반환 형식을 유지하는 경계로 남겼습니다.

입력 판단·답변·검토·법률 용어 설명은 공통 `structured_call`을 사용합니다. 실제 Provider는 native async 호출을 사용하며 동기 테스트 어댑터는 호환합니다. 요청별 계측의 set/reset은 context manager로 모았습니다. 클라이언트 연결 재사용은 모델의 단일 추론 시간을 크게 줄인다는 주장 대신 연결·동시 처리·취소의 개선으로 설명합니다.

## 계측 계약

- `generation_ms`: 문맥 준비부터 최종 초안의 생성·검토·선택까지 전체 구간입니다. 마지막 생성 호출로 덮어쓰지 않습니다.
- `last_generation_call_ms`: 마지막 초안 생성의 SDK 호출 시간입니다.
- `context_ms`, `intake_ms`, `retrieval_ms`: 해당 구간의 시간입니다.
- `model_calls`, `model_stage_ms`, `llm_calls`: 입력·생성·검토·재생성 호출을 기록합니다. 성공 여부와 실제 호출 수를 구분합니다.
- `repair_attempts`, `excluded_claims`: 수정 횟수와 마지막 검토에서 제외 대상으로 판정된 주장 수입니다.
- `unknown_usage_calls`: 취소·실패 등 알려진 usage가 없는 호출 수입니다. 알려진 토큰 합계는 전체 청구 비용이 아니며 임베딩·SDK 내부 재시도·응답 없는 호출을 포함하지 않습니다.
- `first_evidence_ms`, `terminal_ms`: 요청 시작부터 실시간 SSE 수신까지의 시간입니다. 종료 후 계약 검사는 `check_duration_ms`로 따로 기록합니다.

벤치마크는 완료·중단·fallback·계약 실패를 구분합니다. 계약 실패 시 원본을 보존하고 실패 코드로 종료합니다. 요약은 원본 파일 경로를 참조하며 전체 응답을 다시 복제하지 않습니다. 상담 생성 시간과 추가 질문 요청 시간을 섞은 중앙값만으로 성능을 설명하지 않고 `completed_llm`과 시나리오별 결과를 확인합니다.

`cold`는 각 시나리오 전에 로컬 MCP 프로세스를 실제 재시작하고 container ID·시작 시간·healthy 상태를 남깁니다. 이는 프로세스 내 검색·임베딩 캐시가 빈 조건이며 DB·OS·모델 서비스 캐시를 비우는 것은 아닙니다. `primed`는 같은 질문으로 검색 API를 먼저 호출하는 조건이고 TTL·퇴출에 따른 실제 hit는 검증하지 않으므로 확정적인 warm-cache 측정이라고 부르지 않습니다. 캐시 제어 실패도 실패 표본으로 보존합니다.

## 실제 API 결과

기존 설정으로 캐시를 비우고 4건을 실행한 결과 계약 검사는 모두 통과했습니다.

| 시나리오 | 결과 | 종료까지 | 첫 근거 |
| --- | --- | ---: | ---: |
| 주거 | 상담 생성 | 39.282초 | 13.203초 |
| 근로 | 상담 생성 | 47.203초 | 14.578초 |
| 소비자 | 추가 정보 요청 | 10.078초 | 해당 없음 |
| 정보 부족 | 추가 정보 요청 | 6.531초 | 해당 없음 |

이후 임시 Compose override로 세 단계 추론량 `low`와 재생성 0회를 적용해 3건을 실행했습니다. 의미 검토는 계속 수행했습니다. 종료 후 기존 설정으로 복원했고 Backend·MCP·DB·Redis health를 확인했습니다.

| 시나리오 | 결과 | 종료까지 | 첫 근거 | 최종 주장 |
| --- | --- | ---: | ---: | ---: |
| 주거 | 상담 생성 | 23.687초 | 11.656초 | 1개 |
| 소비자 | 상담 생성 | 18.094초 | 4.547초 | 2개 |
| 정보 부족 | 추가 정보 요청 | 5.562초 | 해당 없음 | 없음 |

중복 요청·소유자 분리·실시간 SSE·재생·원문 인용·답변과 인용 주장 일치 검사가 통과했습니다. 주거·소비자에서 마지막 검토의 부분 지지 주장 각각 1개를 제외했습니다. 주거의 검색 자료 ID·본문은 기존 설정 실행과 일치했지만 답변 내용과 범위는 달랐습니다. 소비자의 기존 실행은 추가 질문 분기이므로 상담 생성 시간과 직접 비교하지 않습니다.

각 조건·시나리오의 단일 실행이며 모델의 변동성, 일부 실험의 동시 진행, 여러 설정 변경이 섞인 pilot입니다. 25초 목표가 안정적으로 달성됐거나 법률 정확도가 개선됐다고 발표하지 않습니다. 모든 보고서의 p95는 표본 부족으로 비워 두었습니다.

원본은 `output/latency/live-cold`와 `output/latency/live-fast`에 있습니다. 커밋·dirty 상태는 실행 시점의 정보를 보존하며, 과거 기록을 최종 커밋에서 실행한 것처럼 바꾸지 않습니다.

## 같은 근거를 사용한 비교

처음에는 입력 판단과 생성을 함께 비교했으나 소비자 질문의 입력 판단이 실행마다 달라졌습니다. 이 기록은 `repair-comparison`에 남겼습니다. 추가 정보 요청의 짧은 시간을 재생성 최적화 효과로 계산하지 않습니다. 이후 `--scope intake`와 `--scope answer`로 나누고 답변 비교에서는 입력 판단을 실행하지 않고 같은 저장된 검색 자료를 사용했습니다.

입력 판단은 질문 2개에 대해 설정별 1회 수행했습니다.

| 설정 | 주거 | 소비자 | 관찰 |
| --- | ---: | ---: | --- |
| 기존 gpt-5-mini | 10.465초 | 7.509초 | 두 질문 모두 검색 가능 |
| 같은 모델, 추론량 low | 3.115초 | 4.990초 | 검색 가능, 소비자는 주의 안내 추가 |
| gpt-5-nano, 기본 추론 설정 | 19.886초 | 29.053초 | 이번 실행에서는 더 느림 |

작은 모델로 교체하는 것만으로 빠른 응답을 보장하지 않습니다. 다음 후보는 같은 모델의 낮은 추론량이며, 날짜·금액·증거를 잘못 요구하는지와 자료 부족 판단을 더 많은 질문에서 검토해야 합니다. 모델 지원 기능은 [GPT-5 mini 공식 문서](https://developers.openai.com/api/docs/models/gpt-5-mini)와 [GPT-5 nano 공식 문서](https://developers.openai.com/api/docs/models/gpt-5-nano)를 확인했고, 모델별 추론 설정은 [Reasoning 공식 문서](https://developers.openai.com/api/docs/guides/reasoning)를 참고했습니다.

고정 근거 답변 비교에서는 기존 설정, 재생성 0회, 생성 low, 검토 low, 검토 모델 교체, 최대 문서 4개, 검토 입력 공유를 각각 실행했습니다. 관련 결과 14건은 `answer-comparison/index.json`에서 확인합니다.

- 주거의 기존 설정 실행 1건은 잘못된 span ID로 fallback했습니다. 실패를 숨기지 않았으며 빠른 상담 생성 표본에 포함하지 않습니다.
- 소비자 기존 설정은 20.766초, 재생성 0회는 20.600초였습니다. 둘 다 재생성이 없었으므로 재생성 제한 효과가 입증된 비교가 아닙니다.
- 생성 low는 주거 13.427초·소비자 19.920초로 검토까지 완료했습니다. 답변 초안이 실행마다 달라 충분한 반복과 사람 채점이 필요합니다.
- 검토 모델을 nano로 바꾼 소비자 실행은 수정·재검토를 포함해 79.518초였습니다. 기본 모델 교체 근거로 채택하지 않았습니다.
- 주거는 원래 선택 자료가 3개라 최대 4개 설정이 문맥을 줄이지 않습니다. 소비자는 실제 문서 수가 줄지만 예외·답변 범위 손실 검토가 필요합니다.
- 검토 입력 공유는 주거에서 수정·재검토가 발생했습니다. 문자열 중복 감소가 전체 시간 감소를 보장하지 않으므로 기본값으로 채택하지 않았습니다.

모델 결과는 사람 정답 라벨이 아닙니다. `quality-review.json`은 질문·답변·인용과 비어 있는 채점 항목을 포함하고 `quality-review-key.json`은 설정 대응표입니다. 설정명을 가린 상태에서 두 평가자가 입력 판단·질문 충족·인용 지지·예외 보존·보류 적절성을 확인하도록 준비했습니다. 사람이 채점한 결과를 작성하지 않았습니다.

## 재현 명령

```powershell
./scripts/test_all.ps1
.venv/Scripts/python.exe scripts/benchmark_analysis.py --repeats 1 --cache-state cold --output-dir output/latency/new-live
.venv/Scripts/python.exe scripts/compare_latency.py --scope answer --scenarios 0 2 --variants baseline repair0 --max-calls 16 --output-dir output/latency/new-answer
.venv/Scripts/python.exe scripts/compare_latency.py --scope intake --scenarios 0 2 --variants baseline intake_low --max-calls 8 --output-dir output/latency/new-intake
.venv/Scripts/python.exe scripts/review_latency.py output/latency/new-answer
```

비교 도구는 시나리오·반복·논리 호출 수를 제한하고, 설정을 임시 변경한 뒤 예외가 나도 원복합니다. SDK는 논리 호출당 네트워크 재시도 최대 1회를 허용합니다. 입력 판단의 형식 재시도는 최대 1회이며 같은 입력 판단 시간 예산 안에서 실행됩니다. 실제 API 실험은 호출 비용이 발생합니다.

빠른 설정을 로컬에서 확인하려면 아래 예시 파일을 명시적으로 적용합니다. 실제 실행한 설정과 같은 구성이며, 사람의 품질 검토 전에는 공개 배포 기본값으로 채택하지 않습니다.

```powershell
docker compose -f compose.yml -f compose.latency.example.yml up -d --no-deps backend
# 실험 종료 후 복원
docker compose up -d --no-deps backend
```

원문 인용 검증, 의미 검토, 미지지 주장 제외, 소유자 분리, 추가 질문 요청은 계속 유지합니다. SDK 호출 취소가 서버 측 처리·청구 취소를 보장하지는 않습니다. 근거 부족 fallback이나 일부 주장 제외를 완전한 법률 답변으로 설명하지 않습니다.

## 검증과 다음 작업

최종 전체 회귀 테스트는 **289개 통과·4개 제외**입니다. 합성 시계로 전체 생성 구간이 마지막 SDK 시간으로 덮어써지지 않는지, 재생성 0·1회와 문맥 1회 구성, 알려지지 않은 span 거부, 부분 주장 제외, 비동기 취소, 연결 재사용·종료, 계측 분리, 실패 결과 보존과 실험 설정 원복을 검증했습니다.

다음 순서는 개발 질문 확대 → 사람 채점 → 선택한 두 설정 반복 → 독립 평가 → 기본값 결정입니다. 짧은 응답만 고르거나 실패·추가 질문을 상담 성공 시간에 섞지 않습니다. 입력 판단 메시지와 검토 이유의 출력 길이 제한은 별도 한 항목 실험으로 남겼습니다. quotes 호환 모드 제거와 Worker·큐·공개 배포는 이번 범위에서 실행하지 않았습니다.
