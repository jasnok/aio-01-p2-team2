# 로컬 메모리 저장소의 만료 자료 정리

## 문제와 수정

Redis를 사용하지 않는 로컬 개발 환경에서 로그인 토큰, 비회원 분석 이력, 법률 용어 결과는 메모리 딕셔너리에 저장된다. 기존에는 만료된 바로 그 키를 다시 조회해야 제거되었다. 새 세션이 계속 생겨도 다시 조회되지 않는 만료 항목은 메모리에 남았다.

세 저장소가 새 항목을 저장할 때 기존 잠금 안에서 현재 `monotonic()` 시각을 한 번 읽고, `expires_at <= now`인 항목을 정리한다. 이후 같은 시각을 기준으로 새 TTL을 설정한다. 공통 함수는 유효한 항목을 제거하지 않는다. 비회원의 동일 세션 재저장은 유효한 이력을 유지하며 TTL을 갱신한다. 이미 만료된 세션의 재저장은 이전 기록을 이어받지 않는다.

Redis 저장·조회·CAS·TTL 처리, 법률 용어 결과의 소유권 확인, 로그인 토큰 생성 방식에는 변경을 넣지 않았다.

## 검증

`backend/tests/test_memory_session_expiry.py`에서 실제 저장소의 공개 저장·조회 메서드를 사용한다. 대기 대신 시계를 제어한다.

- 세 저장소마다 조회하지 않은 만료 항목 200개를 만든 뒤 새 저장으로 제거되는지 확인한다.
- 만료 경계인 시각에도 제거되며, 다른 유효 항목과 새 항목은 보존된다.
- 세 저장소마다 32개 동시 저장 이후 모든 새 항목을 조회할 수 있다.
- 비회원 분석·용어 대화의 TTL 갱신, 다른 세션의 보존, 만료 후 새 이력 시작을 확인한다.

기존 코드에서 만료 항목 제거를 검사하는 6개 테스트가 실패했고 수정 후 통과했다. 기존 비회원 이력·소유권·결과 저장 회귀 테스트와 전체 PostgreSQL·Redis 통합 테스트를 함께 검증한다.

## 운영 범위와 한계

정리는 해당 저장소의 **다음 저장 시** 수행된다. 유휴 상태에서 타이머가 자동으로 삭제하는 기능은 추가하지 않았다. 조회 시 해당 만료 키를 제거하는 기존 동작도 유지한다. 유효 항목의 개수·바이트 상한을 추가한 것은 아니므로 이를 총 메모리 상한으로 해석하면 안 된다.

한 번의 정리는 해당 저장소의 항목 수에 비례한다. 이는 로컬 개발용 메모리 경로이며, 운영 공유 상태에는 기존 Redis TTL을 사용한다. 요청 지연이나 RSS 개선 수치는 측정하지 않았으므로 주장하지 않는다. 새 스케줄러·백그라운드 작업·캐시 프레임워크는 추가하지 않았다.
