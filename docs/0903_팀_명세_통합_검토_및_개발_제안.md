# 법률 사례 검색 AI Agent — 팀 명세 통합 검토 및 개발 제안

## 1. 전체 평가

현재 업로드된 **통합 계획서 + DB/RAG 명세 + MCP 명세 + Redis 명세 + 역할 분담 + Frontend 화면 시안**을 서로 대조해보면, 전체 구조는 꽤 잘 잡혀 있다.

특히 각자 따로 작성한 명세가 하나의 시스템으로 연결되는 편이고, 개발 기간이 짧은 프로젝트에서 가장 중요한 **역할 경계와 데이터 전달 지점**이 비교적 명확하다.

다만 실제 개발 들어가기 전에 **5~6개 정도는 팀 전체가 한 번 더 확정하고 시작하는 것이 좋다.** 그렇지 않으면 각자 코드는 잘 만들었지만 통합 과정에서 타입, ID, 응답 구조가 서로 안 맞는 상황이 생길 수 있다.

---

## 2. 전체 시스템 구조

현재 시스템은 사실상 다음과 같이 정리할 수 있다.

```text
[사용자]
   ↓
[상옥]
Frontend / Streamlit
   ↓
HTTP API
   ↓
[다혁]
FastAPI / Backend
Agent
   ↓
MCP Client
   ↓
[병훈]
Legal MCP Server
   ↓
Tool
├─ search_cases
├─ search_legal_documents
├─ get_case_detail
└─ get_law_article
   ↓
[지혜]
PostgreSQL + pgvector
├─ legal_documents
├─ legal_chunks
└─ ingestion_runs

          +

[Redis]
최근 대화 / 실행 상태 / Tool Timeline / Cache
```

아키텍처 자체를 지금 와서 크게 바꿀 필요는 없다.

## 3. 역할 분담 평가

4명의 역할 분리는 자연스럽게 잘 나뉘어 있다.

| 담당 | 책임 | 산출물 |
|---|---|---|
| 상옥 | 사용자 화면 | Streamlit UI |
| 다혁 | 요청 처리 / Agent | FastAPI + Agent |
| 병훈 | 검색 인터페이스 | MCP Server + Tools |
| 지혜 | 데이터 / RAG | PostgreSQL + pgvector |
| Redis | 보조 인프라 | Context / Timeline / Cache |

특히 MCP 담당이 시스템 중앙에 위치한다는 점이 중요하다.

```text
지혜
DB / RAG
   ↓
[ DB ↔ MCP 계약 ]
   ↓
병훈
MCP Tool
   ↓
[ MCP ↔ Backend 계약 ]
   ↓
다혁
Agent
```

따라서 MCP 담당은 양쪽 인터페이스를 모두 확인해야 한다.

핵심 역할은 다음과 같이 구분한다.

```text
MCP
= 실제 검색 담당

Agent
= 어떤 검색을 할지 판단
```

Backend와 Agent는 DB에 직접 접근하지 않는 구조를 유지한다.

---

## 4. DB ↔ MCP 구조 평가

DB 설계는 다음과 같이 구분되어 있다.

```text
legal_documents
→ 원문 + metadata

legal_chunks
→ Chunk + Embedding

ingestion_runs
→ 데이터 수집 기록
```

`legal_documents`에는 판례 검색 결과 화면에 필요한 다음과 같은 필드가 들어간다.

```text
case_number
case_name
court
decided_at
judgment_result
summary
source_url
```

MCP의 `search_cases`는 이 데이터를 꺼내도록 되어 있다.

```text
legal_chunks
     ↓
vector similarity

JOIN

legal_documents
     ↓

document_id
case_number
case_name
court
decided_at
judgment_result
summary
source_url
similarity
```

따라서 **DB 담당자가 만든 데이터를 MCP 담당자가 어떻게 사용할지**가 문서상으로 연결되어 있다.

---

## 5. Frontend 화면과 Backend/MCP 구조의 연결

현재 LawPath 화면의 핵심 구성은 다음과 같다.

```text
내 사례 분석

AI 상황 요약

관련 법령

유사 판례 TOP 3

실제 판결 결과

쉬운 법률 용어

필요 서류

다음 행동

FAQ
```

이 UI는 단순한 시안이 아니라 현재 Backend/MCP 구조에서 실제로 공급 가능한 데이터로 구성되어 있다.

예를 들어 유사 판례 카드에는 다음 정보가 필요하다.

```text
case_number
case_name
court
decided_at
judgment_result
similarity
```

이 값들은 MCP `search_cases`에서 반환할 수 있다.

따라서 Frontend 화면 시안이 실제 구현 구조와 따로 놀고 있지는 않다.

---

## 6. 법률 서비스 안전 정책

현재 설계에서 중요한 정책은 그대로 유지하는 것이 좋다.

### 허용

```text
검색된 판례에서는 원고가 일부 승소했습니다.
```

### 금지

```text
당신은 승소합니다.
승소 확률은 80%입니다.
이 사건은 반드시 패소합니다.
```

Frontend에서도 다음처럼 명확하게 표현해야 한다.

```text
이 판례의 실제 판결 결과
```

또한 화면 하단이나 결과 영역에 다음 의미의 안내 문구를 유지한다.

```text
본 서비스는 법률 자문이 아니며 실제 사건의 승소/패소를 예측하지 않습니다.
```

## 7. Redis 설계 평가

Redis는 주 DB가 아니라 보조 계층으로 사용하는 방향이 적절하다.

```text
PostgreSQL
├─ 법령
├─ 판례
├─ Chunk
├─ Embedding
└─ 영구 이력

Redis
├─ 최근 대화
├─ Request Status
├─ Tool Timeline
└─ RAG Cache
```

Redis를 이용하면 다음과 같은 진행 상태를 사용자에게 보여줄 수 있다.

```text
질문을 분석하고 있습니다.
        ↓
관련 법령을 검색하고 있습니다.
        ↓
유사 판례를 검색하고 있습니다.
        ↓
관련 자료 3건을 찾았습니다.
        ↓
답변을 작성하고 있습니다.
```

다만 Redis, SSE, Stream은 핵심 기능보다 후순위로 둔다.

MVP에서는 Redis List를 사용하고, SSE/Redis Stream은 시간이 남을 때 확장하는 것이 적절하다.

## 8. 가장 중요한 추가 문서 — Team Contract

현재 각 파트 설계는 잘 되어 있지만, 개발 전에 **통합 계약서**를 하나 더 만드는 것을 권장한다.

예:

```text
=========================
TEAM CONTRACT v1
=========================

CATEGORY

housing
labor
consumer


DOCUMENT_TYPE

LAW
CASE
GUIDELINE


Frontend → Backend

POST /api/legal/questions

{
    category,
    question,
    session_id
}


Backend → MCP

search_cases(
    query,
    category,
    top_k
)


MCP → Backend

{
    success,
    data,
    meta,
    error
}


Case Item

{
    document_id,
    case_number,
    case_name,
    court,
    decided_at,
    judgment_result,
    summary,
    source_url,
    similarity
}


Backend → Frontend

{
    request_id,
    status,
    category,
    question_summary,
    answer,
    laws,
    cases,
    sources,
    follow_up_questions,
    recommended_documents,
    next_step_checklist,
    disclaimer
}
```

이 계약을 확정해두면 각 담당자는 다음처럼 개발할 수 있다.

```text
상옥
→ Frontend에서는 cases 배열을 읽는다.

다혁
→ MCP 결과를 Backend Response로 변환한다.

병훈
→ MCP에서 정해진 Schema로 반환한다.

지혜
→ DB에서 필요한 필드를 제공한다.
```

기능 추가보다 이 계약을 먼저 확정하는 것이 중요하다.

## 9. ID 정책 확정 필요

현재 DB에는 다음 두 ID가 존재한다.

```text
id
external_id
```

MCP에서는 다음 값을 사용한다.

```text
document_id
```

Redis에서도 다음처럼 사용한다.

```text
document_ids
```

따라서 팀에서 ID의 의미를 명확하게 정해야 한다.

권장안:

```text
id
→ DB 내부 PK

external_id
→ 국가법령정보 API ID

document_id
→ 시스템 내부에서 사용하는 공개 ID
```

예:

```text
CASE-000001
LAW-000023
```

또는 MVP에서는 DB PK를 그대로 `document_id`로 사용해도 된다.

중요한 것은 **팀 전체가 같은 의미로 사용해야 한다는 것**이다.

## 10. Embedding 모델 통일

DB 적재 시 사용한 Embedding Model과 MCP가 사용자 Query를 Embedding할 때 사용하는 Model은 반드시 동일해야 한다.

예:

```text
EMBEDDING_PROVIDER=ollama
EMBEDDING_MODEL=...
EMBEDDING_DIMENSION=...
```

핵심 조건:

```text
DB 적재 시 Embedding Model
=
MCP Query Embedding Model
```

이 값이 다르면 Vector Search 결과를 신뢰할 수 없다.

## 11. Hybrid Search 가중치

현재 초기 설계는 다음과 같다.

```text
Vector Search 70%
Keyword Search 30%
```

이 방향 자체는 괜찮다.

다만 발표 시에는 고정된 최적값처럼 표현하기보다 다음처럼 표현하는 것이 좋다.

```text
MVP 초기 가중치

vector_weight = 0.7
keyword_weight = 0.3
```

시간이 남으면 테스트 질문을 이용해 가중치를 조정한다.

이렇게 하면 외부 API 문제 때문에 전체 프로젝트가 멈추는 상황을 줄일 수 있다.

## 13. 개발 순서 단순화

첫 번째 개발 목표는 다음 End-to-End 흐름 하나를 성공시키는 것이다.

```text
사용자

"퇴직금을 못 받았어요."

        ↓

Frontend

        ↓

Backend

        ↓

LaborAgent

        ↓

search_cases

        ↓

MCP

        ↓

pgvector

        ↓

판례 3개

        ↓

Agent

        ↓

Backend

        ↓

Frontend

        ↓

```

이 흐름이 성공하기 전에는 FAQ, SSE, Redis Cache, 음성, 질의 이력 같은 부가기능은 잠시 미뤄도 된다.

이 End-to-End 흐름이 프로젝트의 핵심이다.

## 16. 개발 전 최종 확정할 6가지

코딩 시작 전에 팀 전체가 다음 여섯 가지를 확정하는 것을 권장한다.

```text
1. category 값
   housing / labor / consumer

2. document_id 의미
   DB PK인지 별도 시스템 ID인지

3. DB → MCP Schema

4. MCP → Backend Schema

5. Backend → Frontend Schema

6. Embedding Model / Dimension
```

이 여섯 가지가 맞으면 각 담당자는 독립적으로 개발해도 통합하기 쉬워진다.

## 17. 최종 평가

현재 기획과 역할 분리는 실제 개발 가능한 수준까지 내려와 있다.

특히 다음 구조의 책임 경계가 잘 잡혀 있다.

```text
DB / RAG
 ↓
MCP
 ↓
Agent / Backend
 ↓
Frontend
```

Redis도 핵심 데이터베이스가 아니라 보조 계층으로 분리되어 있어 구조적으로 깔끔하다.

지금부터는 명세를 계속 늘리기보다 실제 코드를 붙이는 단계로 넘어가는 것이 적절하다.

MCP 담당 기준으로는 다음 순서로 개발을 시작하면 된다.

```text
DB가 준비됐다고 가정

database.py
 ↓
repository.py
 ↓
search_cases
 ↓
MCP Server
```

현재 LawPath 화면은 이 End-to-End가 연결됐을 때 보여줄 최종 결과 화면으로 충분히 좋은 방향이다.
