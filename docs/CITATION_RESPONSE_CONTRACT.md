# 주장·인용 응답 계약

## 문제

기존 `LegalQuestionView.cited_claims`는 임의 딕셔너리 목록이었다. 빈 객체, 누락된 `citations`, 숫자 또는 빈 `text`, 누락되거나 잘못된 `quote`도 HTTP·SSE·저장 이력의 계약 검사를 통과했다. 화면과 PDF는 해당 필드를 직접 읽으므로 잘못된 응답이 렌더링 실패로 이어질 수 있었다.

## 변경

프론트엔드 공통 모델에 `CitedClaimView`와 `ClaimCitationView`를 추가했다.

- 주장의 `text`는 비어 있지 않은 엄격한 문자열이다.
- 각 주장은 최소 한 개의 인용을 가진다.
- 인용의 `evidence_id`는 비어 있지 않은 엄격한 문자열이다.
- `quote`는 1~2400자 엄격한 문자열이며 현재 백엔드 `ClaimCitation` 길이 계약과 일치한다.

동기 분석의 `ask_legal_question`, SSE 완료 결과의 `final_result`, 저장 이력의 `HistoryItemView.result`가 같은 모델을 사용하므로 세 경계에 동일하게 적용된다. 잘못된 결과는 기존 `CONTRACT_MISMATCH` 예외 안내로 변환된다. JSON 직렬화 후 필드 구조는 그대로 유지하며, 인용 필드가 없는 과거 결과나 빈 인용 목록도 계속 허용한다.

## 검증과 한계

`frontend/tests/test_citation_contract.py`에서 14종의 잘못된 인용을 세 실제 응답 경계에 전달했다. 수정 전 42개 테스트가 실패했고, 수정 후 모두 통과했다. 세 경계에서 정상 인용·빈 인용·인용 필드 없는 결과의 JSON 구조와 원본 입력 불변성을 함께 검증한다. 기존 PDF·저장 이력 회귀 테스트도 유지한다.

이 검사는 응답 구조의 유효성을 보장한다. 원문과 인용의 일치, 근거 ID의 실제 존재, 주장의 법률적 타당성은 별도 문제이며 기존 백엔드 근거 검증과 사람의 품질 평가를 대체하지 않는다. 새 모델 호출·출처 링크 노출·개인 파일 저장은 추가하지 않는다.
